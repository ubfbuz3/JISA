## 2. 编辑决定意味着什么

这是 **Reject, updates required before resubmission**，即拒稿后允许修改重投，不是正式的 Minor Revision。信中只给一次重投机会；没有写明确切重投截止日期，不应自行补一个日期。IEEE Access 当前官方说明也明确其二元决定制度与一次重投机会，参见 [Stages of Peer Review](https://ieeeaccess.ieee.org/authors/stages-of-peer-review/) 和 [Reviewer Guidelines](https://ieeeaccess.ieee.org/reviewers/reviewer-guidelines/)。

R1 认可知识贡献与技术价值，R2 认可测量批评和透明制品；二者共同质疑的是贡献增量和结论边界。这些肯定说明可以保留核心问题，并不意味着修改后必然录用。

编辑要求最终准备三类材料。第一类为逐条回复，每项包含 concern、response、actual action。第二类为全部个别改动均高亮的 PDF，包括语法改动，附件推荐黄色高亮。第三类为干净可编辑源文件和干净 PDF。新增补充材料也应随本次重投供审阅。当前附件模板将两位审稿人放在同一回复文件内，可按其模板组织，但每位的答复仍应独立完整，不相互引用另一位的意见。作者不变时无需新增作者变更程序。

## 3. 比审稿意见更应优先处理的六个问题

### 3.1 合成研究没有真正实现正文所称的“snapshot/live”因子

正文 `sections/03_protocol.tex` 把两个 GUI mode 解释为冻结爬取快照与执行时实时状态。代码 `experiments/run_matrix.py` 实际设置 `GUI_MODES = ("blind", "aware")`，而 `experiments/mrs/mstwi_mrs.py` 中：

- blind 对 MR-002 恒置 cannotReach 为真，对 MR-004 恒置 canRetrieve 为假。
- aware 在执行时请求当前的 `GET /doc` 列表。
- `setup_scenario` 已在执行 MR 前完成共享或带外 seed；runner 没有先采集并冻结 M(t0)、再授权变更的阶段。

**所以这 576 条记录能支持列举可见性、框架账本盲区和裁决行为的受控分析，不能原样解释成一次只改变读取时间的时序实验。** 最短修法是将旧合成研究准确改称可见性/账本实验，保留真实系统承担时序证据；推荐另增加真正的 crawl→grant/revoke→request 协议，分别存储 M(t0)、M(t1) 和授权版本。新旧数据应分开发布，不要把旧 blind 记录重命名为 snapshot 后继续沿用原结论。

### 3.2 真实系统把“成功访问”直接写成了“合法授权”

`run_real.py` 的核心链是 `granted = st == 200`，继而 `truth_map[...] = granted`、`authorized = granted`，再以 `alarm and authorized` 计 false_proofs。Gogs 与 GitLab 的对应代码也采用这种结构。

HTTP 200 是实际访问观测 Y，不是应有授权 E。在 BOLA 研究中，E=0 且 Y=1 恰好是真漏洞。因此重探测同一个资源、将访问者响应与所有者响应比对，可以验证对象内容和访问成功，却不能独立证明访问合法。

这不表示这些真实系统已经存在漏洞，也不表示原有每一格标签都错。问题是**当前落盘的真值判定链没有足够地区分 E 与 Y**，所以“oracle sound on all cells”和 false-proof 数字需要用独立依据重新核验。

修法为在运行前冻结预期有效权限清单，来自明确的拓扑、成功执行的授权事务、继承/角色/可见性规则及独立配置或受控状态记录；不得用待测 GET 的返回值填充 E。每格单独记录 `expected_entitlement`、`observed_effect`、`oracle_answer`、`policy_version` 和来源。验证 E=1 的合法读应结合授权链；验证写操作则记录实际状态变化，不能只用状态码。

### 3.3 命题 2 混淆“oracle 足够判定”与“实际方法完全相同”

`sections/06_boundaries.tex` 从 oracle 足够推出实际 MR 裁决为 f(O,R)，再构造同一函数作为 direct，得到逐点相等。这个构造当然相等，但没有证明实际使用的 v3 与 `direct_observe` 相等。

本次重算确认二者相差 **3 条记录**，不是 9 条或新的独立缺陷。三条都来自同一配置下 S5、MR-002、aware 的三个 exception-policy 版本。actor 只有读权限却成功写入；列表中对象可见使 MR 门控不成立，v3 返回 pass；direct 用成功写入与无写权限判为违规。完整记录已另存 `v3_direct_disagreements.json`。

因此建议把命题 2 改为有条件的“授权判定充分性”说明，并写出实际规则。对同一候选请求、同一时刻且可靠完整的 oracle，可令 `D = Y ∧ deny(O)`，`H_v3 = A_MR ∧ deny(O)`。若被研究的 MR 警报满足 `A_MR ⇒ Y`，则其确认集合包含于 direct 的确认集合；是否严格包含取决于门控和输出比较。**这支持受条件约束的包含关系，不支持自动宣布两种实现逐点等价，更不涉及搜索能力或成本优劣。**

### 3.4 对原论文 specificity 的公式和人工核验描述不准确

本地 MST-wi 原文 `mstwi_paper_text.txt` 在约 3100–3240 行明确说明对每个 MT failure 做人工核验，并给出 `specificity = F_TN/(F_TN+F_FP)`。在其 FN=0 的处理下，等于 `1 - F_FP/(F-F_TP)`，不是当前稿件简写的 `1-FP/全部输入`。

原文可由 [MST-wi 论文](https://arxiv.org/abs/2208.09505) 核对。不能因为其 detector 使用爬取模型，就直接断言论文的最终人工标签也是由爬虫决定，或其 99.81% 只衡量与爬虫的一致性。目前材料没有支持这项指控。

应改成有证据的、较窄的批评：**全局输入级 specificity 不能单独保证每个授权转移场景表现良好；原评估没有建立本文新增时序场景中的性能。** 承认其人工核验，再讨论场景覆盖缺口和权重稀释。用参数敏感性分析替代 84.62% 的拟复现，不从四舍五入的 99.81% 反推精确计数。

### 3.5 v1、弃权及“证明”标签需要与实现对齐

正文把 v1 描述成“raw alarms proven”，但 `boundary_aware.py` 的 v1 实际检查是否存在任何对象共享记录，存在就降为 indeterminate；v2 才进一步匹配权限层级。本次重算得到 raw MR 触发 333 次，实际 v1 确认 258 次，说明它们并非同一方法。应保留真正 raw 行，另给存在性过滤器与权限过滤器准确命名，并重生相关表。

此外，v3 不只在 oracle 不可读时弃权。它在 oracle 显示 covering 时也返回 indeterminate。本次重算有 228 次 indeterminate，其中 156 次因不可读，72 次因合法覆盖共享。正文“只计不可读导致的弃权”不能代表方法全部弃权行为。

原生引擎记录的是 `getFailures()`，它直接证明的是 native MR 产生报警/关系失败。将其称为工具自身宣称 `violation-proven`，还需 upstream 输出契约证据。建议显式分开 native alarm、作者定义的 promotion policy、经独立真值确认的 false proof，避免把自建裁决器的语义归给上游。

### 3.6 结尾的排除式结论与自身阳性结果矛盾

`06_boundaries.tex` 末尾称这些关系的结果只能是假证明、与 direct 相同或弃权，真正非法访问的裁决不在其中。现有合成结果却有 v3 的 105 个 TP，seeded control 也有 TP。与 direct 同样检出真漏洞，依然是正确裁决；“没有增量”不等于“没有能力”。

应删除这句推论。改为分别陈述已验证的合法访问误报机制、完整 oracle 条件下的同候选判定信息充分性，以及未获得验证的广义检测效果。相关旧回复中的同样表达也应放弃，不应继续加强这一结论。

## 5. 推荐的论文重定位与最小有效补证

### 5.1 推荐选择“收窄结论＋针对性补证”

不建议为保留宽标题而仓促扩到 76 条 MR，也不建议维持现有数据只改措辞。推荐保留方法学案例研究，范围明确为两条关系及实际触发的原生子集，同时补足真实时序、独立真值、竞争性差分对照、多种缺陷控制和复现入口。

建议标题为 **When Reachability Misleads Authorization Testing: A Case Study of MST-wi’s Reachability-Gated Relations**。

摘要第一段就写案例对象与范围。避免“MT 是 leading technique”之类未建立的强定位，避免“vulnerable and correct systems answer identically”的无条件表达。可改为“成功响应本身不足以区分合法授权与未授权访问”。数字待独立真值核验后重新选择，只保留最必要的计数及明确分母。84.62% 当前摘要并未出现，满足 R2 的该项要求；还应从 findings 的定量支撑中移出，不能回复成“本轮已从摘要删除”。

新颖性应由一张结构化表定位，列“已有认识／本文具体贡献／证据／不主张什么”。oracle 问题、状态会变、全局指标可能掩盖子组差异均不是新概念。可以争取的增量是**这些认识在具体关系的谓词、门控、授权渠道与判定流程中如何组合，哪些失效可由日志复现，怎样区分 temporal staleness 与 channel incompleteness**。不应声称已经证明所有访问控制 MT 都无法裁决。

已有 [oracle survey](https://philmcminn.com/publications/barr2015.pdf) 是 oracle 问题的背景；[RESTler](https://www.microsoft.com/en-us/research/publication/restler-stateful-rest-api-fuzzing/) 是状态化请求生成的背景；[MST-wi](https://arxiv.org/abs/2208.09505) 是直接研究对象。现有 [BACScan 论文](https://doi.org/10.1145/3719027.3744825) 与[公开实现](https://github.com/LFYSec/BACScan)值得用于竞争性差分/效果观测比较，其修改操作的 oracle 不只比较响应相似性。不要把自建“两账户相似度脚本”写成跑过完整 BACScan。另注意正文把 BACFuzz 放在黑盒线中，而其[作者摘要](https://arxiv.org/abs/2507.15984)明确称 gray-box，应修正分类。

真实漏洞阳性建议从可固定版本、补丁和复现步骤的公开已知案例选择，范围仅本地受控实例。本次尚未选定或跑通具体 CVE，不能预先写结果。至少一个真实 vulnerable/fixed 配对是回应 R2 的有力方案，属于本报告建议，不是信中规定的数目。多个 independently implemented defects 是 R1 的明确关切。若选择不补真实阳性，就要删除一般检测收益/无收益主张，但 R1.7/R1.9 的实证要求仍可能不被认为充分解决。

### 5.3 时间一致性与 oracle admissibility 应变成方法

建立状态 `S_v` 与预期有效授权 `E(S_v,u,o,a)`，显式覆盖直接、team/group、role/admin、public 与共享渠道。grant/revoke 操作改变对应权限边；revocation 不一定消除仍由其他路径获得的权限，不能把“删除一条 grant”简单记为完全无权。

给出 crawl、mutation commit、oracle read、request enforcement、adjudication 的顺序。主实验先在可控静止窗口运行，确认整个请求到判定阶段授权版本不变；并发更新另设实验。请求与 oracle 不在同一状态版本时，应 unknown/retry，不得自动判 FP/TP。仅两次 oracle 回答相同不能排除中间 grant→revoke 的 ABA；需要单调授权版本或完整事件日志支持。

admissibility 应在检测输出出现前确定候选与拒绝条件。先做渠道覆盖，再审查 oracle 与 enforcement 的共享逻辑及缺陷类别，再在独立校准集验证，冻结选择后才运行测试。不同 URL 不等于独立机制；同一个 `can_access` 被两处调用尤其不能证明对继承权限计算缺陷独立。对绕过单一路由检查的 seed，正确 policy engine 可能是合理 oracle；对 policy engine 自身缺陷，它可能与缺陷同源。将结论限定到已验证的系统、渠道和缺陷类。

### 5.4 指标改为“输入级＋场景级诊断”，不把诊断当新 specificity

以每个合法/负类场景 i 的负类请求数 `n_i` 和 false positive 数 `p_i` 为基础，`Sp_micro = 1 - Σp_i/Σn_i`。固定有问题场景的 `p_i`，增加无误报场景的负类请求权重，可使总体值上升；若 detector 同时改变 `p_i`，趋势取决于两者增长率，不是无条件趋于 1。相关性不会改变计数恒等式，但会影响抽样推断；当前固定枚举不需要伪造独立样本置信区间。

新增逐场景 `p_i/n_i`、macro 平均、任意误报场景比例和完全失效场景比例，分别定义。参数图可展示固定 4 个 FP、其余负类输入增加时的变化，但必须标“假设性敏感性示例”，不标“99.81% 的重现”。不管哪种汇总，只要 E 错了，所有指标都可能错；换 denominator 无法修复 oracle validity。

## 7. 正文结构及交付顺序

建议主文按“问题与贡献定位→明确关系/状态/判定语义→受控机制→真实系统授权渠道与时间对照→阳性与公平基线→测量解释→范围及实践建议”组织。将目录普查、全部配置、36/18子集对照、原生异常堆栈、安装细节和异质权重完整推导放 SI 或 artifact。正文保留会改变中心解释的限定，尤其 live 修复结果、oracle 共享缺陷风险和未覆盖的检测机制。避免每个段落重复同一组三层 scope 声明。

新增的 evidence-to-claim 表至少有四行。第一行是源码证明固定数据结构/缓存读取，不等于实验覆盖全部关系。第二行是经独立真值校准后的真实时序机制，不等于场景发生率。第三行是同候选完整 oracle 下的判定充分性，不等于搜索或检测总体无收益。第四行是异质负类输入权重造成聚合遮蔽，不等于原文99.81%计算错误。

实施次序为先修 E/Y 与方法标签，再修真实时序及 oracle 预验证，再做基线/阳性，之后重生全部统计和图，最后统一改标题摘要结论、写逐条回复和制作高亮稿。回复信应在能填写实际动作和位置后定稿，不能先写“we have added”再把补证留空。
