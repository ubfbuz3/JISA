## 三、上传前优先修正的五组问题

### 1. 覆盖率表给同名 direct_only 换了判定规则

对应 RB-M1，主审又独立逐记录复核。

`compute_all.py:523–534` 对 `direct_only` 的定义是仅看 oracle 是否 deny，不看请求是否成功；`direct_observe` 才额外要求请求成功。`ingest_coverage.py:113–123` 却先算 `alarm=(s=='none' and ok)`，然后将同一 alarm 同时用于这两个方法。

因此 Table 4 中 `direct_only` 的零风险不是单纯改变弃权处理或评分分母得到的，而是给方法增加了原来没有的观测条件。依据原定义，312 条可读、已判定记录中实际为：

| 类别 | 条数 |
|---|---:|
| 正确的违规声明 | 108 |
| 没有违规效果却仍作违规声明 | 108 |
| 正确非声明 | 96 |
| 另列不可读弃权 | 264 |
| 已判定集合中的二值声明错误风险 | **108/312 = 34.62%** |

108 个错误声明全部在正确拒绝的请求上，即 E=deny、Y=deny。按论文“严格 false proof 必须 E=allow”的定义，它们不应再次被直接叫作严格 false proof；但也不能被代码悄悄加上 Y 条件消失。

**修正要求** 保持方法定义跨表一致，分别报告严格 false proof 和“无实际越权效果的无效违规声明”，并让风险包含其对应错误；或明确重命名不同方法，不能继续说只是对同一方法换一种评分。增加所有方法跨表判定的一致性核对，而不只核对当前生成宏之间的相等。

公平比较的 `direct_observe`、v3 和三条违规检出差异不因这个错误改变。无需重跑服务。

### 2. unknown/default-deny 的分歧改变评分集合，不能说整体无影响

对应 RA-M1，主审已做字面协议敏感性复算，记录在 `primary_checks.json`。

`03_protocol.tex:84–97` 披露协议 promised unknown、实现返回 deny，然后说两者在已报告运行中 coincide、没有格子的 verdict 依赖该选择。但同段又规定 E unknown 不进入 truth table，评分时排除。原始记录中，所有这些 deny 格的 `expected_channel` 都是 none，basis 都是无 granting channel。

若按文中已经承认的协议字面规则重标，评分集合为：

| 产品 | 当前实现的评分格 | 改为 unknown 的格 | 字面协议下 E 已知且可评分的格 | stale false proofs | live false proofs |
|---|---:|---:|---:|---:|---:|
| Gitea | 280 | 203 | 77 | 13 | 0 |
| GitLab | 432 | 338 | 94 | 16 | 0 |
| 合计 | **712** | **541** | **171** | **29** | **0** |

所以两种规则对记录的 A/H 布尔值和这 29 个错误声明没有影响，但会改变 E 是否已知、可评分集合、truth table 的 E 分类和 E/Y 一致性分母。按实现说 712/712，按字面协议就只能在 E 已知的 171 格上说 171/171，另披露 541 unknown，不能称完全一样。

**修正要求** 保留原协议和原始数据，明确将主分析的 closed-world default-deny 登记为实现采用、需要完整渠道拓扑前提的规则，并补这张双口径敏感性对账。把“无影响”限定为已观察到的 29/0 现象，不延伸到评分分母。无需为消除分歧而回写旧协议或原记录。

### 3. 背景仍误写 privileged recrawl，且 GET-only 范围过宽

对应 RA-m2、RB-m2、C-M3，以及 C-m1。

`02_background.tex:26–30` 仍将修复 29 格的实验称为 privileged recrawl，并暗示同界面重爬不修复。实现对 M0/M1 都使用相同 `self.cl[s]`，实际结果也是 same-credential recrawl 修复全部 29 格。

**修正要求** 区分：授权之后对象可重新列出，是可刷新修复的陈旧；授权之后对象仍永不进入该 crawl source，才是渠道不可见。重新列举对象不要求读取当初发生授权的管理事件，更不等于提高凭证权限。Gogs 的 live 残留可以承载后一个边界，不让 29 个可恢复案例承担该主张。

`05_realsystem.tex:303–306` 以及回信称全部 observation 都是 GET，但两个 runner 的补充写能力探针确有 POST 和 DELETE 清理。将 GET-only 限于模型列举、oracle 和读探针，另列写探针/恢复，并说明它们不改变授权配置。

### 4. 回信总述仍把 111 对 84 称为 matched request budget

细节段和正文已正确说明只有探测对匹配，总请求、信息和权限不同；但回信序言仍称竞争基线在 `matched request budget` 上完成，并没有把 R1.7 列为部分满足/替代回应。

**修正要求** 序言直接写 `matched probe pair, unequal total request and information budgets`，将 R1.7 放入未完全满足原请求的说明。若维持当前有限裁决个案范围，可以说明采用这种对照为何合理、不主张同预算检测优越性，无需为了让标签变 CLOSED 追加竞品大实验。若坚持宣称已满足等总预算要求，才需要相应实际设计。

同时，R1.12 的数学扩展现在已经回答了异质/内生计数的核心数学问题；没有生成机制模型是边界，不宜自动等同于原请求未满足。R2.6 原文要求讨论构造率对设计的依赖，未强制等权重实验。反之，R1.1 的结构化方法学比较仍较弱。不要只机械地把剩余条目压成“五项”，应使每条缺口与审稿原话一致。

### 5. 复现材料尚未完全冻结到历史输入

对应 RB-M2。

`ingest_native_engine.py:51–88` 读取包外 MST 工作区当下的 Git status/log/diff，生成“上游改动 1 个文件、Java 改动 0”等历史执行事实；`compute_all.py:338–389` 还依赖固定绝对路径及该外部仓库当下的 HEAD 内容。外部仓库状态变化会改变“历史运行事实”的输出。Reviewer B 的隔离复算中，14 个步骤均退出成功，但外部 Git 访问失败使源码状态相关字段变为缺值；这不证明作者的原数字错误，却说明输出不全是归档记录的确定函数。

**修正要求** 将可核实的上游版本、源码摘要、实际补丁和改动清单冻结为输入，再由这些输入生成历史事实；实时 Git 状态只作附加诊断。没有历史材料时标明可验证边界，不倒填采集时间。把源码路径参数化，缺少承重来源应非零退出，或明确只复算不含该来源的部分。

另外，普通 `reproduce.sh` 不会自动先校验输入哈希，不能称任意修改输入都会被所有生成器拒绝。应在流水线入口执行输入校验，或将正文合同限定为必须先执行 verify 的流程。`ARTIFACT.md` 仍写 GitHub 尚未创建、12 输入/10 输出，应更新为实际状态。

主审补充确认，92 文件 LaTeX ZIP 中没有原始 JSON/JSONL 和 Python 生成器。因此回信末尾应分别说“源码包可编译”和“完整仓库可从原始记录生成图表”，不能称单独的 92 文件源码包也包含完整实验复算链。
