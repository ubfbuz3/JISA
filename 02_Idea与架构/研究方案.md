## 0. 一句话 Idea

> **把 LLM 从"漏洞判定者"降级为"授权意图假设生成器"，让它把散落在 OpenAPI、路由、鉴权中间件、数据访问代码里的授权规则，归纳成一份带证据出处的可机检授权契约；再用一个带三重阴性对照的确定性差分 oracle 去动态证伪它——从而在 BOLA/BFLA 检测中同时拿到高召回和低误报。**

工作名：**AuthOracle**（授权契约归纳 + 差分证伪）

## 1. 问题定义（Research Question）

**RQ**：在只有 API 规范、源码与部署实例（无人工授权策略文档）的前提下，能否自动推断出应用的**授权意图**，并用可复现的动态证据证明某端点存在 BOLA（对象级越权）/ BFLA（功能级越权）？

拆成三个可独立验证的子问题：

| 编号 | 子问题 | 对应贡献 |
|---|---|---|
| RQ1 | LLM 能否从异构制品中归纳出**可机检**的授权契约，且每条带证据出处？ | 契约归纳 IR + 证据归因 |
| RQ2 | 差分 oracle 相比朴素判定能否显著降低误报？ | 三重阴性对照 oracle |
| RQ3 | 端到端在公开应用上的检测效果、PoC 可复现性与成本如何？ | 工具 + 公开基准 |

## 2. Gap 定位

来自 [文献调研报告](../01_文献调研/文献调研报告.md) 的 Gap 2 + Gap 3 交叉处，这也是 Codex 独立判断的最强 gap。

### 2.1 现有方法各自缺什么

| 代表工作 | 路线 | 致命缺口 |
|---|---|---|
| [1] BolaZ (TOSEM'26) | 静态污点跟踪 resource ID，推授权边界 | **纯静态**；不做"意图"推断，只适配既有的 best-practice 逻辑；不产出运行时可执行证据 |
| [2] OpenAPI→Petri 网 (IJIS'25) | 规格形式化 + 日志分析 | 规格里**根本写不下**真实授权规则（OpenAPI 的 security scheme 只到"要不要 token"这一层） |
| [3] EvoMaster 安全 oracle (JSS'26) | fuzzing 阶段加访问策略违规检查 | 需要**人工告知**角色与策略；不做静态规划；无状态前置条件建模 |

### 2.2 我们的 Gap 陈述

> **授权意图从不被写在同一个地方。** OpenAPI 只声明端点在不在、要不要认证；源码只体现"实现了什么检查"；数据库 schema 只描述归属关系；业务逻辑只存在于人的脑子里。BOLA/BFLA 恰恰产生于**"实现"弱于"意图"**的那个缝隙——而现有工作要么只看静态（知其边界不知其意图），要么只看动态（知其行为不知其应该）。
>
> 尚未有工作把 LLM 用在**跨制品联合归纳授权规则**上，并用**确定性验证器**约束 LLM 幻觉。

### 2.3 为什么这个 gap 值钱

- 三区审稿人最认的叙事：**真实问题 + 新方法 + 可复现实验 + 有实用性**。BOLA 是 OWASP API Security Top 10 的**第 1 名**，实用性无需论证。
- 与 [1] 的区分度清晰：他们是**静态、规则自适应**；我们是**跨制品意图推断 + 动态证伪**。
- 不需要训练大模型 → 算力门槛低，符合 [12] 在 JISA 上被认可的"轻量化"偏好。

## 3. 核心方法

### 3.1 三阶段流水线

```
┌────────────────────────────────────────────────────────────────┐
│ Stage 1  制品收割 (Artifact Harvesting)                         │
│  OpenAPI/Swagger · 路由定义 · 鉴权中间件/装饰器                  │
│  ORM 模型与查询 · 测试夹具 · (可选) 实时流量                     │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌────────────────────────────────────────────────────────────────┐
│ Stage 2  授权契约归纳 (Authorization Contract Induction)  ★C1   │
│  LLM 产出 typed clauses，每条必须附 evidence_ref                │
│  <endpoint, method, actor_role, resource_type, relation,        │
│   action, precondition, evidence_refs>                          │
│  ✗ 无证据出处的 clause 直接丢弃                                  │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌────────────────────────────────────────────────────────────────┐
│ Stage 3  契约编译 + 差分证伪 (Compile & Differential Refute) ★C2│
│  3a 资源生产者/消费者识别 → 获取对象 ID                          │
│  3b 状态前置条件规划（用合法流程把系统推到可触发状态）           │
│  3c N 个身份 + 受控对象创建（归属真值由构造保证）                 │
│  3d 三重阴性对照差分 oracle                                     │
│  3e 最小化 PoC 输出 + 授权缺失位置定位                           │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
              可复现 PoC + 授权契约违反证据
```

### 3.2 ★C1 授权契约归纳：LLM 只做假设，不做裁决

**输入**（统一成"授权证据包"）：
- 端点清单与参数（OpenAPI / 路由表）
- 每个端点链路上的鉴权代码片段（中间件、decorator、guard、`@PreAuthorize`）
- 资源对象的归属字段与查询条件（ORM 模型、SQL）
- 角色/权限的声明位置（枚举、配置、种子数据）

**输出**：一份类型化的授权契约

```
Clause := {
  endpoint:      "GET /api/v1/orders/{orderId}",
  actor_role:    "regular_user",
  resource_type: "Order",
  relation:      "owner",          # owner | member_of | role_at_least | public
  action:        "read",
  precondition:  ["order.status != 'deleted'"],
  source:        [impl:OrderController.java:88, spec:openapi.yaml#/orders/{id}],
  confidence:    0.0-1.0
}
```

三条硬规则（这是防幻觉的关键）：
1. **每条 clause 必须带 `source`**，指回具体文件行号或规范路径。无法出处 → 丢弃。
2. **`relation` 必须来自受控词表**，不接受自然语言自由发挥——否则无法编译成测试。
3. **LLM 不输出"有漏洞/没漏洞"的判断**，只输出"我推测的授权规则是什么、依据在哪"。

### 3.3 ★C2 三重阴性对照差分 oracle（本文最硬的技术点）

这是直接对着 Gap 3/Gap 7 里点名的**误报问题**设计的。

**难点**：BOLA 的判定天然歧义——身份 B 访问 A 的对象，返回 403、404、200 空体、200 带错误码，都可能。朴素做法（"没返回 4xx 就算越权"）误报率极高。

**解法**：用三个对照建立"该应用的语义基线"，再做差分。

| 对照 | 请求 | 目的 |
|---|---|---|
| **Control-1 自访问** | B 访问 **B 自己**的对象 | 证明请求格式合法、身份有效、端点可达 |
| **Control-2 幽灵对象** | B 访问**不存在**的对象 ID | 提取该应用的"拒绝签名"（区分 403 / 404 / 业务错误码） |
| **Control-3 重复稳定性** | 重复 Control-1/2 各 k 次 | 排除限流、缓存、环境抖动导致的偶发差异 |
| **Test** | B 访问 **A 的对象** | 与三个对照做差分 |

**判决规则**（确定性，无 LLM 参与）：

```
violation  ⟺  Test 的响应语义签名 == Control-1 的成功签名
            ∧ Test 的响应语义签名 ≠ Control-2 的拒绝签名
            ∧ Control-1 / Control-2 在 k 次重复下稳定
```

**"响应语义签名"** = 对响应做结构化归一：状态码 + 业务错误码字段 + 响应体 schema 形状 + 关键字段是否非空 + 数据归属字段是否为 A 的标识。**而不是**简单的状态码比较。

**为什么这是贡献**：
- 把误报从"启发式阈值问题"变成"差分判定问题"，可量化、可消融。
- 消融实验直接可做：去掉对照 → 误报率飙升（预期能从 40%+ 降到 <10%），这是审稿人爱看的那张图。

### 3.4 状态前置条件规划（区别于 [3] 的关键）

大量 BOLA 需要状态可达：订单得先创建、状态得是 `pending` 才能被改、购物车得有商品。做法：
- 从契约的 `precondition` 字段 + ORM 约束反推需要哪些前置对象；
- 用**受控创建流程**满足：每个身份通过合法 API 流程创建自己的资源；
- 顺带解决**归属真值问题**——因为对象是我们看着创建的，owner 是构造出来的 ground truth，不靠人工标注。

这一招同时干掉 Gap 1 里"标签主观"的坑。

## 4. 数据集与实验设计

### 4.1 公开被测应用（全部 Docker 化，保证可复现）

| 应用 | 类型 | 为什么选它 |
|---|---|---|
| **OWASP crAPI** | REST，多用户，专为 API Top 10 设计 | 官方 BOLA/BFLA 教学靶场，有社区公认的漏洞清单 |
| **VAmPI** | Flask REST，多用户 | 经典 BOLA/IDOR 靶场，代码量小易于消融 |
| **DVGA** | GraphQL | 补上 GraphQL 维度，证明方法不绑 REST |
| **OWASP Juice Shop** | 大型全栈 | 规模化验证 + 真实复杂度，含 BOLA 相关挑战 |
| **Spring PetClinic REST** | 正常业务应用 | **阴性样本**：用来测误报（不能把正常应用报成漏洞） |
| **[3] 的 WFD 语料** | 36 个 REST API | 与 EvoMaster 系基线直接可比（可用性需核对原文） |

### 4.2 自建基准（Gap 1 的回应）

**AuthBench**：8–12 个应用 × 注入的已知 BOLA/BFLA 缺陷 + 同数量的"安全孪生端点"作阴性对照。

- 缺陷注入方式：在开源应用上**定向削弱**归属校验（如把 `WHERE id=? AND user_id=?` 改成 `WHERE id=?`），并保留改动前后的 diff 作为真值证据。
- 优点：真值来自**代码 diff**，客观可审计，不是人工标注。
- 公开：Docker 镜像 + 注入清单 + 预期检出表，挂 GitHub/HuggingFace。

> ⚠️ 诚实性标注：注入型基准有"人造"风险，因此**必须以真实开源应用上的真实 CVE 复现作为第二组实验**（对照 [1] 的做法），否则审稿人会攻击。

### 4.3 Baselines

| 类别 | 具体 |
|---|---|
| 静态分析 | BolaZ [1]（若开源；否则按其论文思想复现 ID 污点启发式） |
| 规格形式化 | OpenAPI→Petri 网 [2] 的思路 |
| Fuzzing oracle | EvoMaster + 安全 oracle [3]；RESTler / Schemathesis 状态式测试 |
| 规则扫描 | Semgrep 缺归属校验规则集 |
| 朴素动态 | 随机 ID 替换 / 相邻 ID 替换 |
| **纯 LLM 基线** ★ | 让 LLM 直接看代码+规范判"是否有越权"，不执行（证明验证器的价值） |
| 无对照差分 | 我们的方法去掉三重对照（内部消融，暴露误报） |

**纯 LLM 基线是必须的**——[10] 已经证明 LLM 在检测任务上并不天然更强，这个对照能同时回应审稿人和文献。

### 4.4 评价指标

- **检出**：Precision / Recall / F1，粒度 = (端点 × 角色 × 对象归属关系)
- **误报率 FPR** ★ 主指标（在 PetClinic 等阴性应用上的错误报警密度）
- **PoC 有效性**：重跑 k 次的可复现率 + 最小攻击序列长度
- **状态可达率**：前置条件成功建立的比例
- **成本**：每 API 的 LLM token 消耗、端到端墙钟时间
- **LLM 规模敏感性**：7B 轻量模型 vs API 大模型的效果差（呼应 [12]）

### 4.5 消融实验（审稿人必问，提前做）

1. −契约归纳（只用 OpenAPI）→ 召回掉多少
2. −证据归因（放开 LLM 自由生成）→ 幻觉率、误报率
3. −三重对照（朴素 oracle）→ **FPR 变化（预期最大的一条）**
4. −状态前置规划 → 可达率与召回
5. 不同关系类型（owner / role / tenant）的分别贡献
6. 跨框架泛化：FastAPI / Spring Boot / Django / Express 各测一轮

## 6. 风险自检（先替审稿人骂自己）

| 风险 | 被攻击的角度 | 应对 |

| 与 [1] BolaZ 撞车 | "这不就是 BolaZ + LLM？" | 明确差异：他们是**静态 + 规则自适应**；我们是**跨制品意图归纳 + 动态证伪**。消融里加"仅静态"对照 |

## 8. 备选 Idea（若主方案受阻）

### 备选 A：跨制品授权策略不一致性挖掘（测量型）
- **一句话**：系统化度量 OpenAPI 声明、代码鉴权实现、测试用例三者之间的授权语义不一致，并量化其与 BOLA 的相关性。
- **优点**：不需要 LLM，工作量可控，动机实验即可撑起半篇。
- **缺点**：偏测量/实证，JISA 对"纯测量"的创新判定偏保守；适合作为主方案的**第 3 章备胎**。

### 备选 B：状态感知的 BOLA fuzzing oracle（工程型）
- **一句话**：不依赖 LLM，用状态机 + 对象归属图增强 REST API fuzzing 的 oracle，构造"攻击者—受害者—资源—端点序列"。
- **优点**：完全可复现，PoC 说服力强，风险最低。
- **缺点**：与 [3] 距离较近，需要靠 BFLA/多租户/跨端点等非平凡案例拉开差距。

### ❌ 不建议的方向：通用 LLM 漏洞检测
[6]–[10] 已经把这条赛道挤满，且 [10] 明确指出 LLM 在该任务上**并不稳定优于传统模型**。在 JISA 上做"又一个 LLM 检测器"，大概率被判为增量工作。
