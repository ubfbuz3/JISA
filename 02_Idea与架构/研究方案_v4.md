## 2. 核心机制：可判定性边界（本次新增，决定方案生死）

> 这一节直接回答追问的判词：
> 「所谓『边界』尚未给出独立政策输入下何种证据构成必要/充分裁决条件，也未证明其超过一般多账户测试、差分与弃权报告的组合。」
> **本节要做的，正是把"边界"从比喻变成一套可机检的判别程序。**

### 2.1 问题的重构：从「判定」到「辨识」

设应用的实际授权政策为谓词 `P(i, o, e) ∈ {0,1}`：主体 `i` 对对象 `o` 执行操作 `e` 是否被授权。BOLA 的定义是 `P(i, o_A, e) = 0` 而访问却成功。

v3 的困境在于：**`P` 没有独立来源。** 它试图用 ORM 的 owner 字段、SQL 的 owner 谓词去近似 `P`——但这些是**实现制品**，不是政策。追问击中此处：

> 「作者却以代码 span 和 owner 字段替代该规格，未证其等价。」

**v4 的重构**：别再问 `P(i, o_A, e)` 等于什么。改问：

> 给定观测集合 `O`，令 `Π(O)` 为**全部与 `O` 一致的政策**的集合。
> `(i, o_A, e)` 是**可判定的** ⟺ 对所有 `P ∈ Π(O)`，`P(i, o_A, e)` 取值相同。

这个转换带来三个性质，正是 v3 缺的：

1. **不需要政策真值**——判据只涉及"一致政策的集合"是否为单点。
2. **可证伪**——要证明不可判定，给出两个政策假设即可；要证明可判定，需给出辨识性论证。
3. **弃权变成定理**——弃权不再是我们能力不足的自陈，而是**"存在多个一致政策"的构造性证明**。

> **这就是"边界"的实质**：边界不是一条凭经验画的线，而是**由证据构型的辨识能力决定的**。
> 某些证据构型（如"同资源上多方法响应不一致"）在原理上不具备辨识力；另一些（如"同一政策下多通道冗余"）具备。

### 2.2 判据 A · 配对不变性（Paired Invariance）

**适用**：存在一对端点 `(e, e')`，**除授权检查外同构**（构造性保证）。

**条件**：
- (a) `i` 在 `e` 上访问 `o_A` 成功；
- (b) `i` 在 `e'` 上访问**同构资源**被拒（403/404）；
- (c) **基线一致**：`i` 对自有对象在 `e` 与 `e'` 上行为相同（排除"`e'` 完全不可用"的平凡解释）。

**辨识性论证**：由 (a)(b) 知 `e` 与 `e'` 的行为存在差异；由构造性保证，两者唯一差异是授权检查位置。故行为差异的**唯一可能归因**是授权检查的取值不同。参照 (b) 处 `P` 拒绝的取值，`P(i, o_A, e)` 应为 `0`，而 (a) 显示实际允许 → **违反**。∎

**实例（也是 L2 孪生的新语义）**：VAmPI 官方 `vulnerable=0/1` 开关给出的正是这样的对——同一份代码、同一份 OpenAPI 3 规格、同一套端点、同一套 DB 结构，**唯一差异是授权检查**。
> ⚠️ v3 把孪生当"阴性对照"用于统计 FPR；v4 把它当**判据 A 的一个实例**用于逻辑推导。**这是性质不同的用法**——前者给频率，后者给判定。
> 排除清单仍须预注册（起点 `/users/v1/_debug`），因为排除清单影响的是"哪些端点构成合法的 `(e, e')` 对"，不是统计分母。

### 2.3 判据 B · 跨通道一致性（Cross-Channel Consistency）★ 本方案最核心的机制

**适用**：应用对同一对象提供 ≥2 条**应当共享同一政策**的读取通道。

| 通道 | 形式 | 语义 |
|---|---|---|
| `c₁` 直接对象访问 | `GET /res/{id}` | 按标识取对象 |
| `c₂` 集合枚举 | `GET /res` | 取"调用者可见的对象集" |

**条件**：
- (a) `c₁`：`i` 成功取到 `o_A` 的内容（且含受害者稳定唯一字段，排除"公共同 schema 记录"解释，见 §5.6）；
- (b) `c₂`：`o_A ∉ S_i`，其中 `S_i` 是 `i` 的枚举结果；
- (c) **加固**：`S_i` 非空且**包含 `i` 自己的对象**——排除"列表被过滤/分页/仅显示近期"的平凡解释。

**辨识性论证**：设一致政策 `P` 存在，并设应用在两条通道上使用同一政策（**通道一致性**——这是实现一致性的必要条件，与政策内容无关）。
- 情形 1：`P(i, o_A, read) = 1` → `c₂` 应把 `o_A` 纳入 `S_i`，与 (b) 矛盾；
- 情形 2：`P(i, o_A, read) = 0` → `c₁` 不应返回 `o_A`，与 (a) 矛盾。
- 两情形均矛盾 → **不存在一致政策** → 实现内部不一致 → **缺陷存在**。∎

**为什么这是本方案最有分量的机制**：它是**唯一一个不依赖政策真值、也不需要配对端点，就能证明"缺陷存在"的判据**。

因为矛盾是**自证**的：无论正确政策是什么，两条通道都给出了相反答案。fault 306 无法做到这一点——见 §2.5。

**可反驳性**：攻击点只有一个——"通道一致性假设"。反驳者须给出一个政策，使两条通道结果自洽（例如声称 `c₂` 是有意的"仅显示最近访问"视图）。**加固条件 (c) 专门用于封堵这一反驳**：若 `i` 更早创建的自有对象出现在 `S_i` 中，则"近期视图"解释被证伪。

### 2.4 判据 C · 状态转移不可逆（Irreversibility）—— 只给「事实」，不给「违规」

**适用**：写操作（`PUT` / `PATCH` / `DELETE`）。

**条件**：
- (a) `i` 对 `o_A` 的写请求返回 2xx；
- (b) `A` 以**独立会话**随后观测到 `o_A` 的状态或存在性变化；
- (c) 基线：`i` 对自有同类对象的同样操作也成功。

**结论**：`cross-account-write-observed`（跨账户写**已发生**）。

> ⚠️ **这是事实，不是违规。** 单独由判据 C 只能排除"请求被静默丢弃"与"响应误导"两种解释，**无法排除"该操作有意开放"**。
> 要升级为 `violation-proven`，必须叠加判据 A 或 B。**v4 强制这个分层，v3 的 `confirmed-write` 在此被拆开**——这是主张降格的技术落点（§3）。

### 2.5 fault 306 落在不可判定区——形式化证明

**EvoMaster fault 306 的启发式**（原文）：同一资源上，若 `i` 做 `PUT` 被 403、`PATCH` 被 403，而 `DELETE` 却成功 → "quite suspicious"。

**证明该证据构型不可判定**：构造两个政策：

| | `P(i, o_A, PUT/PATCH)` | `P(i, o_A, DELETE)` | 是否与观测一致 | 是否 BOLA |
|---|---|---|---|---|
| `W₁` | 0（应有检查） | 0，**但实现漏检** | ✅ | **是** |
| `W₂` | 0（有意保留给 owner） | **1（政策有意允许可见者删除）** | ✅ | **否** |

观测完全相同（403 / 403 / 200），`W₁` 与 `W₂` 都与观测一致且结论相反 → `(i, o_A, DELETE)` **不可判定**。∎

**因此 fault 306 的输出必然是"可疑"**——这不是实现缺陷，而是**证据构型的原理限制**。它自己的命名 `Likely Should Had Been Protected` 恰好与这个结论吻合。

**由此得到本方案最干净的一组对比**（也是"与已有测试框架的差异"的硬答案）：

| | fault 306 的证据构型 | 判据 B 的证据构型 |
|---|---|---|
| 观测 | **单一通道**（直接访问）上，多方法响应不一致 | **同一政策下，多通道冗余** |
| 是否可被一个合法政策完全解释 | **是**（`W₂`） | **否**（矛盾自证，无政策可解释） |
| 原理结论 | 只能输出"可疑" | 可输出"缺陷存在" |

> **这组对比就是"可判定边界"的可执行形式**：边界不是经验阈值，而是**"是否存在一个与观测一致的政策能解释该证据"**。
> 能 → 不可判定（给不可能性见证）；不能 → 可判定。

### 2.6 裁决程序（可机检、不依赖 LLM、不依赖政策真值）

```
输入：候选 (i, o_A, e)，观测集 O
───────────────────────────────────────────────
1. 若 (e, e') 构成同构对 且 满足判据 A(a)(b)(c)
       → violation-proven (paired)         [证据：e/e' 响应 + 构造性同构说明]
2. 否则若存在通道 c₁/c₂ 且 满足判据 B(a)(b)(c)
       → violation-proven (inconsistent)   [证据：两通道响应 + 自身对象在 S_i 中的锚点]
3. 否则若满足判据 C(a)(b)(c)
       → cross-account-observed            [证据：写响应 + 受害者侧观测 + 基线]
4. 否则
       → undecidable                        [必须附不可能性见证：W₁, W₂ + 一致性检查]
───────────────────────────────────────────────
输出：verdict + 判据编号 + 证据引用；禁止在无判据时输出任何 confirmed 类结论
```

**这个程序本身就是可反驳的**：任何一条 `violation-proven` 都可以被"给出一个一致政策"反驳；任何一条 `undecidable` 都可以被"给出一个可判定判据"反驳。**追问要求的"可执行、可反驳的裁决规则"，就在这里。**

### 2.7 与已有机制的差异（追问的硬性要求）

| 已有做法 | 它给什么 | 本方案给什么 |
|---|---|---|
| 双账户交换 / 变形测试 | "**行为不同**" | 行为不同 **+ 辨识性论证**：何时"不同"**必然**意味着政策违反 |
| 差分测试（ACBreaker 的三层差分） | 状态码迁移 + 响应相似度**阈值** | 用**一致性矛盾**替代阈值——无需调参，且矛盾是自证的 |
| 弃权 / confidence（BACScan 的反馈 oracle、NeO 的 sufficiency） | "信心不够" | **不可能性见证**（可独立复核、可反驳） |
| fault 306 的启发式 | 方法间不一致 → "可疑" | **证明它落在不可判定区**，并给出使其可判定的充分条件 |

## 5. 追问缺口的补丁

### 5.1 G1 · 合法跨账户访问负例（追问第二层必做项）

**设计目标**：构造一对端点，其**表面行为与 BOLA 完全相同**，但一端合法、一端非法。

| 配对 | 端点 A（**合法**） | 端点 B（**非法**） |
|---|---|---|
| 输入 | `GET /doc/{id}`，`i` 取 `o_A` | `GET /doc/{id}`，`i` 取 `o_A` |
| 表面行为 | 返回内容 | 返回内容 |
| 自有对象 | 成功 | 成功 |
| 幽灵对象 | 拒绝 | 拒绝 |
| 差异 | 存在**显式共享授权**（`i` 在 `o_A` 的 ACL 中） | **省略授权检查** |

**判定标准（写进预注册）**：
- 若方法无法区分 → **C2 被自己的实验证伪**（这是**好事**：证明它是可证伪的，且说明判据在"合法共享"场景下失效）；
- 若能区分 → 必须说明**依据什么特征**，且该特征**不能是人工给定的政策**。合法一侧应被 §2.3 的加固条件 (c) 自然排除：`i` 的枚举结果 `S_i` **包含** `o_A`（因为共享授权使 `o_A` 确实对 `i` 可见）→ 判据 B 条件 (b) 不成立 → 不给 `violation-proven`。

> **这一条同时给判据 B 提供了第二个可反驳点**：若共享授权下 `S_i` 仍不含 `o_A`，则判据 B 会产生误判 → 必须报告该失效模式。

**扩展负例（同批构造）**：管理员角色、代理/委派（`i` 代表 `u_A` 操作）两种语义，同样做表面行为匹配。

### 5.2 G2 · L0 标注协议（追问 Critical）

追问原话：「两名标注者切出不同数量时，『规格缺口占比』凭什么还是可证伪的量？」

**协议（动笔前冻结）**：

| 项 | 规定 |
|---|---|
| **切分单位** | 以「**端点 × 操作 × 主体角色**」为一个判定单元（三元组）。同一单元内所有授权约束合并计数 |
| **clause 定义** | 该三元组被允许，当且仅当**一组条件的合取**成立；每个不可再分的原子条件 = 1 条 clause（原子 = 单一主体-属性/对象-属性比较） |
| **标注者** | 2 名，独立标注，**不得交流** |
| **盲法** | 标注者**只能看到 OpenAPI 规格与端点文档**，不得看源码、不得看本方案的方法输出（避免"按方法能力标注"） |
| **仲裁** | 分歧由第 3 人裁定；**仲裁前先记录原始分歧** |
| **一致性报告** | 报告 Cohen's κ；**κ < 0.6 则该单元作废**（不进入分母） |
| **分母** | 只统计**κ 达标**的单元；作废单元数量单独报告 |
| **可证伪性来源** | 因切分单位已固定为三元组、原子条件已定义，两人切分数不一致只可能来自"原子性判断"分歧，而这正是 κ 要测量的对象——**κ 达标的单元上，占比是可复现的量** |

### 5.3 G4 · 与 EvoMaster 的可比性（追问 Critical）

追问原话：「它输出『疑似』、本方案输出 `confirmed`，是不同语义的告警集合。」

**v4 处置**：不做"谁更好"的比较，改为**两个正交的问题**：

| 问题 | 做法 |
|---|---|
| **(i) 共同真值集上的配对精度** | 在**独立审计产出**的共同真值集上（人工审计 + L3 构造式真值，**不含两工具的输出**），按**应用配对**比较：`(我们的 violation-proven 集合)` 与 `(EvoMaster 306 告警集合)` 分别对照真值。报告 per-app 精度散点，不汇总总分 |
| **(ii) 可判定区覆盖对照** | 这是 v4 新增、更有说服力的对照：对每个真值阳性，检查**它落在二者的哪个 verdict 类**。EvoMaster 的构型在原理上只能给 `suspicious`（§2.5 已证），所以问题变成：**有多少真阳性被它标为 `suspicious` 而被我们标为 `violation-proven`**。这是一个**集合划分**的对照，不涉及 precision 的定义争议 |

**抽样与未检出项处置**（预注册）：未检出项**不得**从分母剔除；EvoMaster 的 `suspicious` 但未触发告警的场景，逐项记录其触发条件是否满足。

### 5.4 G8 · C2 效度分层修正（追问 Critical）

追问原话：C2 是核心效度主张，却主要挂在 L2（**不是真阴性层**）。

**v4 修正**：

| 主张 | v3 挂靠 | **v4 挂靠** |
|---|---|---|
| C2 的主证据 | L2 孪生静默 | **L3 构造式真值层**（owner 是我们看着产生的，且我们同时构造合法配对，见 §5.1） |
| L2 孪生的角色 | 核心效度证据 | **判据 A 的一个实例**（证明判据可执行）+ 适用边界报告 |
| L2 的诚实声明 | 自称阴性对照 | 明确写：**L2 不是真阴性层**（官方自承 secure 模式仍有缺陷），其价值在于**同构配对**而非"无缺陷基线" |

### 5.5 U4 · 证据图内部冲突的优先权规则

追问原话：「ORM 字段、SQL 谓词、路由参数、运行时对象不一致时，谁有优先权？」

**v4 处置：不需要优先权规则——冲突即弃权。**

理由：任何"优先权规则"都是一次**未经论证的政策推断**（正是追问批评的"以实现制品替代规格"）。v4 的立场是：
- 证据图用于**建立对象归属与状态可观测性**（判据的输入），不用于**推断政策**；
- 若多条证据冲突 → 该点的观测不一致 → **无法保证观测集本身可靠** → 落入 `undecidable`，并记录冲突类型作为诊断信息。

> 这个处置同时消解了追问的 L5-Q3（"是否只是把不可判定性转移到规格抽取？"）：**v4 不再做规格抽取，因而不转移问题——它显式地把这类冲突暴露为弃权原因。**

### 5.6 U6 + L2-Q4 · `confirmed-read` 的对象身份问题

追问原话：「若响应含公共字段、脱敏、分页导致签名变化，如何证明『读到的是受害者对象』？」

**v4 处置**：判据 B 条件 (a) 收紧为——

> 返回内容必须含**至少一个由我们构造的、仅存在于 `o_A` 的唯一标识符**（例如创建时写入的随机 nonce 字段），**或**返回对象在其他独立通道（`c₂`／受害者会话）中可被同一唯一标识符定位。

若无法建立这种唯一标识 → 条件 (a) 不成立 → **不给 `violation-proven`**，降为 `cross-account-observed` 或 `undecidable`。

## 6. 实验设计（v4）

> 方法本体（阶段 0–2 的确定性证据抽取与状态搭建）**沿用 v2 §3**，但**阶段 3 的裁决层被 §2 完全替换**（分层 verdict → 判据裁决程序）。

### 6.1 数据分层（保留 v3 的 L0–L4，调整角色）

| 层 | 内容 | 度量什么 | 真值来源 |
|---|---|---|---|
| **L0 动机层** | crAPI、VAmPI + 4~6 个含多账户认证的 WFD SUT | 「规格缺口占比」（按 §5.2 协议） | 人工标注（双人 + 仲裁 + κ） |
| **L1 官方真值层** | crAPI 官方 challenges、VAmPI 官方 9 项清单 | 官方承认的缺陷能否被找到 | 官方文档 |
| **L2 配对实例层** | VAmPI `vulnerable=1`(:5002) vs `vulnerable=0`(:5001) | **判据 A 的可执行性** + 配对行为一致性 | 官方特性（非注入） |
| **L3 构造式真值层** ★ | 可容器化 API：注入 BOLA + **对应合法配对（§5.1）** + 修复版 | **C2 的主证据**：precision / recall / **弃权率** + 置信区间 | 构造式（owner 看着产生） |
| **L4 规模与现实层** | WFD（=EMB）REST SUT | 触发率 + 可判定区占比（**verdict 分布**，非 precision） | 无 BOLA 标注 → 仅分诊 |

**三条硬性纪律**（保留 v3）：L1–L4 分开报告禁止合并总分；L1 官方清单非穷尽、不当分母；L4 无 BOLA 真值、只服务规模与 verdict 分布。

### 6.2 baseline 矩阵（不变，仅补 G4 口径）

| 优先级 | baseline | 可运行 | 比较口径 |
|---|---|---|---|
| 主 | **EvoMaster 安全 oracle**（306/304/307/308/310） | ✅ | §5.3 的两个正交问题 |
| 主 | 朴素双账户 ID/字段替换 | ✅ 自实现 | 对照"无判据的差分" |
| 主 | 纯规则抽取（**无 LLM**） | ✅ 自实现 | 回答「LLM 环节是否必要」 |
| 主 | 纯 LLM 端到端判定 | ✅ 自实现 | 证明"判定不能交给 LLM" |
| 主 ★新 | **fault 306 启发式的独立复现** | ✅ 自实现 | **直接验证 §2.5 的证明**：其在 L3 上应产生大量 `suspicious` 而无法给出判定 |
| 次 | BolaRay | ⚠️ 高成本 | 先做可行性探测（限时） |
| — | BACFuzz / BolaZ / MOCGuard / ACBreaker / NeO / Udd26 | ❌ | related work，**明确写 artifact 未公开，绝不伪造数值比较** |

### 6.3 预注册成功标准（v4）

1. **判据可执行性**：判据 A/B/C 在 L2 + L3 上**均能被实例化**，且每个 `violation-proven` 都附判据编号与证据引用；
2. **弃权率**：报告点估计 + 置信区间；**预注册上限 50%**（超过则说明方法不实用，须如实报告）；
3. **不可能性见证的完备性**：每个 `undecidable` 都附 `W₁/W₂` 并做一致性检查；**抽查 20% 由独立复核者验证**；
4. **fault 306 的对照**：在 L3 真阳性集上，报告"它标 `suspicious` 而我们标 `violation-proven`"的占比（§5.3(ii)）；
5. **合法配对不失真**（§5.1）：在合法侧端点上报出判据的**失效模式**；
6. **LLM 环节单独报告**：syntax validity / evidence-span validity / 与人工标注一致性；
7. **L3 的每个 `violation-proven` 可重放**：重放脚本 + 对象创建记录 + 三组对照响应 + 最小化 PoC。
