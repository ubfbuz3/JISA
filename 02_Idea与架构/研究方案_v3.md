## 2. 立论基石：把"规格缺失"钉成可引用的硬事实

这是本次核查最有价值的发现。**SOTA 公开工具自己的文档，替我们把动机写好了。**
EvoMaster `docs/faults.md`，fault code **306**：

> **306 | Allowed To Modify Resource That Likely Should Had Been Protected**
> "…access policies could be arbitrarily complex, where some users might validly interact with some resources of other users. A common example is 'administrator' users.
> **Without a formal specification describing in details the access policies in place, it is hard to say automatically if we are in the case of a BOLA/BFLA vulnerability. Still, some heuristics could be used to flag highly suspicious cases.**
> For example, if a user is blocked with a 403 to do a PUT and a PATCH on a resource, it would be quite suspicious if a DELETE would work just fine on that resource."

三个可直接落笔的点：

1. 这个 oracle 的名字是 **"Likely Should Had Been Protected"**——**命名本身承认这是猜测，不是判定**；
2. **"Without a formal specification… it is hard to say automatically"**——公开主线工具**自陈缺少访问策略规格输入**；
3. 它退守的启发式是「PUT/PATCH 被 403、DELETE 却成功 → 很可疑」——**没有对象归属证据、没有多账户差分、只有方法间不一致**。

> **论文动机段可以直接这样写**：BOLA 判定的瓶颈不是"跑不到端点"，而是**缺少把请求行为映射到授权规格的桥梁**。
> 当前最成熟的公开 oracle 对此的处置是**退回启发式并自称"可疑"**（引 fault 306 原文）。
> 我们补上这座桥，并把"可疑"升级为**有分级、有证据、可机检**的裁决。

### 2.1 三条 claim（v3 的贡献结构）

| # | Claim | 可证伪方式 |
|---|---|---|
| **C1** | **规格缺口可量化**：在真实 API 上，决定一个端点访问权所需的授权 clause，有相当比例**既无法用 OpenAPI 表达、也无法被 EvoMaster 类启发式覆盖** | 动机实验（§4.1 L0）给出硬数字；这是全文的立论基石 |
| **C2** | **状态校准能把"可疑"升级为分级结论**：以「自有对象成功签名 / 幽灵对象拒绝签名」做校准后，跨账户请求可被判为 `confirmed-read` / `confirmed-write` / `likely` / `inconclusive`，且在**官方安全孪生**上保持静默 | §4.1 L2 孪生实验 + §4.4 消融 2 |
| **C3** | **可复现的 BOLA 评测协议**：分层（有官方真值 / 安全孪生 / 构造式真值 / 规模现实），**分层报告不合并总分** | 完整的 §4 可被第三方按 version pin 重跑 |

> **不声称**：不声称"发现更多漏洞"，不声称"推断出开发者意图"，不声称"首创差分"。
> 唯一的贡献主张是：**把判定从启发式猜疑，变成有规格依据的可机检裁决——并且让这件事可被重复评测。**

## 3. 竞品差异（v3 修订：补 MOCGuard，标注可运行性）

| 工作 | 它做了什么 | 它没做什么 | 我们的差异 | 可运行? |
|---|---|---|---|---|
| **EvoMaster 安全 oracle**[Sah26] | 37 个 fault code（10 个 security），含 306(BOLA/BFLA 疑似)、304、307、308、310；52 个 API | **无形式化访问策略规格输入**（其文档自陈）；306 只输出"可疑"；无对象归属证据；无多账户差分 | 提供**带证据出处的 clause** 作为规格输入 + 校准裁决，把"可疑"升级为分级结论 | ✅ **主 baseline** |
| **MOCGuard**[Liu25c] ⭐新 | IEEE S&P'25。**数据中心**：从 DB 结构推断用户拥有数据 + **SQL/Java 跨层** owner-check 审计；37 应用、**161 确证 0-day、73 CVE**；比 MACE-Java P↑31.31% / R↑242.55%；~76 s/应用 | **纯静态**（CodeQL）；Java only；不产生运行时证据；不处理"检查存在但错误"之外的运行时语义 | **运行时 + 状态校准**；跨语言（REST/JVM）；结论可回读 PoC | ❌ 未公开 |
| **BolaRay**[Hua24] | SQL + 静态分析推断四类授权模型；25 个 PHP 应用；193 真漏洞 / **FPR 21.86%** / 52 CVE | **FPR 21.86%**；**不支持 SELECT**（为压 FP 而刻意忽略）；**需人工标 DAL 规格**；只能找"缺失"检查 | 覆盖读路径；无需人工规格（自动带证据生成）；动态裁决降 FP | ⚠️ 代码可得，**运行成本高**（Python 2 + Neo4j 2.1.8 + phpjoern） |
| **BACFuzz**[Dha25] | LLM 选参 + 运行时插桩 + **SQL oracle**；20 PHP 应用；16/17 已知 + 26 新；11 FP | 不处理 **SELECT 读泄露**与复杂状态前置；不归纳 clause；不输出归属证据 | 纳入读路径；确定性状态搭建；输出归属证据 | ❌ **artifact 未公开** |
| **ACBreaker**[Wan25d] | LLM 抽取 + fuzzer + 三层差分；11 IoT 设备、508 接口、39 漏洞 | oracle 靠**状态码迁移 + 响应相似度阈值**；不做多账户对象归属 | 用「自有/幽灵」校准替代相似度阈值；做真正的归属判定 | ❌ 未公开 |
| **Udd26** | policy-enriched **IR** 约束 GPT-5 生成可执行授权测试；微服务；drift-validation 97.4% error-free | 目标是**微服务策略漂移**，不是单体 API 的 BOLA 判定；无构造式归属真值 | 任务域不同；评测端到端 precision/recall 而非 drift validation 率 | ❌ 未公开 |
| **NeO**[Li26g] | LLM + 程序分析 + SMT 检测跨服务权限提升；25 项目、6.2 MLOC，P=81.0%/R=85.0% | **终局判断仍含 LLM**（sufficiency assessment） | 判定完全交给确定性 oracle，可报告「LLM 参与度 = 0 的裁决占比」 | ❌ 未公开 |
| **BACScan**[Liu25b] | 黑盒 feedback-driven oracle（推断操作相关页面 + 操作反馈）；20 应用、89 漏洞 / 35 CVE | 黑盒，无源码级证据；无 clause 级解释 | 输出「哪条 clause 被违反 + 证据跨度」 | ❌ 未公开 |

**关键判断（v3 强化）**：竞品里**只有 EvoMaster 可跑**，而它恰好是**唯一与我们把立论对上的**——
其余全是"发现更多漏洞"型工作，任务域、语言、真值、确认流程都不同，**数值不可比**。
所以 v3 的策略是：**不跟它们比数字，跟 EvoMaster 比"结论的确定性等级"，并在同语料上做 paired 比较。**

## 4. 实验设计（v3 重写）

> 方法本体（阶段 0–3、分层 verdict、形式化定义）**沿用 v2 §3，未改动**，此处只重写实验部分。

### 4.1 数据集与实验分层

| 层 | 内容 | 度量什么 | 真值来源 | 可得性 |
|---|---|---|---|---|
| **L0 动机层**（新） | crAPI、VAmPI + 4~6 个含多账户认证的 WFD SUT | **规格缺口占比**：每个受保护端点需多少条授权 clause；其中多少条 (i) 可用 OpenAPI 表达 (ii) 被 EvoMaster 306/304/307 类启发式覆盖 | 人工标注 clause（双人 + 分歧仲裁） | 待筛 SUT（**不得假设**） |
| **L1 官方真值层** | crAPI（官方 challenges：BOLA×2、BFLA×1、Mass Assignment×2…）、VAmPI（官方 9 项清单） | **recall 的分子来源** | 官方 `docs/challenges.md` / README | ✅ |
| **L2 安全孪生层**（核心仪器） | VAmPI `vulnerable=1`(:5002) vs `vulnerable=0`(:5001)，官方 compose 同时起 | **FPR**：合格 oracle 必须 5002 命中、5001 静默 | 官方特性（非注入） | ✅ |
| **L3 构造式真值层** | 少量可容器化 API 注入 BOLA + 对应修复版；version pin + mutation diff + blind protocol | precision / recall / FPR + **置信区间** | 构造式（owner 是我们看着产生的） | 自建 |
| **L4 规模与现实层** | **WFD（=EMB）的 REST SUT** + 可独立复现的真实 CVE | 触发率 + 人工分诊 precision；现实性 | 无 BOLA 标注 → 分诊 | ✅ |

**三条硬性纪律**：

1. **L1–L4 分开报告，禁止合并成单一总分。**
2. **L1 的官方清单是"教学挑战"，不是穷尽清单** → 只能用于"官方承认的缺陷我们找不找得到"，**不能当分母算 recall**。
3. **L4 的 WFD 没有 BOLA 真值** → 它**只服务 FPR / 触发率 / 规模**，**不服务 recall**。这是本方案对语料的诚实定位。

#### L2 为什么是核心（v3 最重要的实验设计改进）

VAmPI 的 `vulnerable` 开关给出的是：**同一份代码、同一份 OpenAPI 3 规格、同一套端点、同一套 DB 结构，只切换授权检查。**

- 这是**应用级配对的阴性对照**，证据层级高于 v2 的**请求级**幽灵对象对照；
- 它是**官方特性，不是我们注入的缺陷** → 直接削弱 v2 风险表里最凶的攻击「自建 benchmark 是人为注入，不代表真实」；
- 度量形式干净：**5002 命中 ∧ 5001 静默** → 可算成一个明确的通过/失败率。

> ⚠️ **必须预注册排除清单**：官方文档自承安全模式并非完全干净——
> "even in secure mode (`vulnerable=0`), some endpoints may still have vulnerabilities due to inherent bad practices in their implementation, such as the debug endpoint."
> 起点：`/users/v1/_debug`。**排除清单须在实验开始前冻结并公开**，否则这些端点会被误计为 FP。

### 4.2 baseline 矩阵（v3 重写：按可运行性排序）

| 优先级 | baseline | 可运行 | 为什么是它 |
|---|---|---|---|
| **主** | **EvoMaster 安全 oracle**（306/304/307/308/310） | ✅ | **唯一可跑的同语料公开对照**。它的输出是"可疑告警"，我们的输出是分级裁决 → 直接量化"从可疑到确证"的增益 |
| **主** | 朴素双账户 ID/字段替换 | ✅ 自实现 | 最小对照，完全可控 |
| **主** | 纯规则/静态抽取 clause（**无 LLM**） | ✅ 自实现 | 回答「LLM 环节到底必不必要」——打不过就把它降级为可选排序器 |
| **主** | 纯 LLM 端到端判定 | ✅ 自实现 | 审稿人必问的对照；同时证明"判定不能交给 LLM" |
| 次 | BolaRay[Hua24] | ⚠️ 高成本 | **先做可行性探测**（容器里跑通 1 个 PHP 应用）。跑通才承诺比较，且只在**重叠应用子集 + 共同对象集**上报 |
| — | BACFuzz / BolaZ / MOCGuard / ACBreaker / NeO / Udd26 | ❌ | **移出 baseline，进 related work**，明确写「artifact 未公开，无法公平比较」。**绝不伪造数值比较** |

> **这条替代路线的合法性**：Sah26 用了 WFD（36 API），我们同样用 WFD；
> 它可跑、公开、且其文档自陈限制。**与一个能跑的、同语料的、限制被官方写明的工具做 paired 比较，比与六个跑不起来的工具比数字要强得多。**

### 4.3 预注册成功标准（v3 修订）

实验前冻结，避免事后挑选：

1. **EvoMaster 对照**：在**相同请求预算**下，我们的分级裁决相对其 306 告警，**precision 显著提升且 recall 不出现大幅牺牲**（按应用配对，不汇总请求数）；
2. **孪生静默**：在 VAmPI `vulnerable=0` 上，**静默率**（未产生 confirmed 级误报的比例）报告点估计 + 置信区间；排除清单公开；
3. **每个 TP 可重放**：重放脚本 + 攻击者/受害者对象创建记录 + 三组对照响应 + 最小化 PoC；
4. **LLM clause 单独报告**：syntax validity、evidence-span validity、与人工标注一致性——**不报端到端 F1 了事**；
5. **L1–L4 分层报告**，L4 明确标注"无真值、仅供分诊"。
   （v2 第 5 条"与 ≥1 个最强可运行基线 paired 比较"**已由第 1 条吸收**。）

### 4.4 消融矩阵（沿用 v2，标注优先级）

| # | 消融 | 回答什么 | 优先级 |
|---|---|---|---|
| 2 | **去掉幽灵对象对照** | FPR 是不是靠对照压下去的（**预期最强的一张图**） | ★★★ |
| 4 | **LLM clause → 纯规则抽取** | LLM 是否真的必要 | ★★★ |
| 6 | 分层 verdict → 退化成单一布尔 | 分层是否真的降低误报 | ★★ |
| 1 | 去掉 clause（用通用 BOLA 模板） | clause 归纳有没有用 | ★★ |
| 3 | 去掉重复稳定性门 | 异步/限流噪声影响多大 | ★★ |
| 5 | 单账户 vs 双账户 | 差分本身的价值 | ★ |
| 7 | 确定性状态搭建 vs LLM planner | 谁更可靠 | ★ |

## 7. 下一步（按"能否决定方案生死"排序）

1. **启动 Docker → 跑通 VAmPI 双实例**（`:5001` secure / `:5002` vulnerable，两侧都 `GET /createdb`），
   确认 5001/5002 的行为差异与官方描述一致。**这是全部实验的第 0 步，卡住则一切停摆。**
