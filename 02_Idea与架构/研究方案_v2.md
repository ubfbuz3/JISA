## 1. 重新定位：不卖 LLM，卖 oracle

### 1.1 一句话命题

> **Evidence-grounded, state-calibrated oracle for BOLA detection**
> （面向 BOLA 检测的、有证据支撑且状态校准的判定 oracle）

### 1.2 唯一可防守的贡献

v1 的主线是「LLM 归纳授权契约」。这条线已经被占了，而且占它的工作做得不差。v2 把主线换成：

> 在**已部署、可控的单体 REST 应用**中，从带出处的候选 clause 自动编译出
> 「受害者 — 攻击者 — 同构对象 — 幽灵对象」的**状态化**测试；
> 只有当跨账户请求与攻击者自有对象的成功语义一致、与幽灵对象的拒绝语义可区分、
> 且重复执行稳定时，才判为 BOLA。

这是一个 **oracle 校准 + 构造式真值** 的贡献，不是 LLM 贡献。

### 1.3 角色降级：LLM 从主角变配角

LLM 在新方案里的职责被压缩到**只做受控 candidate ranking**：

- 输入是**确定性抽取出来的证据图**（不是原始代码全文）
- 输出是**受控词表上的 relation 选择**，JSON Schema 约束
- 每一条输出必须绑定 source span，否则丢弃
- **永远不做漏洞判定**，且论文必须单独报告它的 clause 正确率

如果消融实验显示「LLM 环节打不过纯规则/纯静态基线」，方案仍然成立——LLM 降级为可选排序器，
论文靠 oracle + benchmark 立住。**这是本方案的风险对冲设计。**

## 2. 与最强竞品的逐项差异

审稿人一定会拿这几篇对比。差异必须逐项写清，不能含糊。

| 工作 | 它做了什么 | 它没做什么 | 我们的差异 | 数字 |
|---|---|---|---|---|
| **BACFuzz**[Dha25] | LLM 选参 + 运行时插桩 + **SQL oracle**；20 个 PHP 应用，检出 16/17 已知问题、26 个新问题 | 明确不处理 **SELECT 型读泄露**与**复杂状态前置**；LLM 不归纳 clause；不输出对象归属证据 | ①把读路径（SELECT）纳入可证伪范围；②用 producer-consumer 图确定性搭建状态；③输出可回读的对象归属 PoC | 11 FP |
| **ACBreaker**[Wan25d] | LLM 抽取代码语义 + fuzzer + 三层差分过滤；11 个 IoT 设备、508 接口、39 漏洞 | oracle 主要靠**状态码迁移 + 响应相似度阈值**；目标是 protected-interface evasion，**不做多账户对象归属** | 用「自有对象 / 幽灵对象」校准替代相似度阈值；做真正的多账户归属判定 | nomore403=4，Boofuzz=0 |
| **Udd26** | policy-enriched **IR** 约束 GPT-5 生成**可执行授权测试**；微服务、drift-validation 97.4% error-free | 目标是**微服务策略漂移**，不是单体 API 的 BOLA/BFLA 判定；无构造式对象归属真值 | 任务域不同（单体 REST + 对象归属），且我们评测端到端 precision/recall 而非 drift validation 率 | — |
| **BolaRay**[Hua24] | SQL + 静态分析推断四类对象授权模型；25 个 PHP 应用，**193 真漏洞 / 52 CVE** | **FPR 21.86%**；刻意忽略 SELECT（为降 FP）；只能找"缺失"检查，不能找"错误"检查；要人工标 DAL 规格 | 动态裁决把 FPR 压下去；覆盖 SELECT 读路径；无需人工 DAL 标注 | FPR 21.86% |
| **NeO**[Li26g] | LLM + 程序分析 + SMT 检测跨服务权限提升；25 项目、6.2 MLOC，P=81.0% / R=85.0% | **终局判断仍含 LLM**（LLM sufficiency assessment）；不处理端点运行时对象归属 | 判定完全交给确定性 oracle，可报告「LLM 参与度 = 0 的裁决占比」 | P 81% / R 85% |
| **BACScan**[Liu25b] | 黑盒 feedback-driven oracle（推断操作相关页面 + 操作反馈）；20 应用，89 漏洞 / 35 CVE | 黑盒，无源码级证据；不产出 clause 级别的解释 | 输出「哪条 clause 被违反 + 证据跨度」，可解释性更强 | 89 / 35 |
| **EvoMaster 安全 oracle**[3] | 把 access-policy violation oracle 接进开源 fuzzer；52 个 API（9 人工 + 8 靶场 + 36 WFD） | 需要角色/策略输入（**具体机制待核对原文**） | 我们的 clause 由证据图自动生成 | — |

**关键判断**：我们**不需要**在"发现漏洞数量"上赢——那是不可比的（语言、应用、真值、确认流程都不同）。
我们要赢的是 **precision / FPR / 可复现性 / inconclusive 率**这几个可比的指标。

## 3. 修订后的方法设计

### 3.1 总体流程

```
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 0  证据抽取（100% 确定性，无 LLM）                          │
│   OpenAPI 规格 + 路由表 + 鉴权中间件/decorator + ORM 归属字段    │
│   + SQL predicate + role 字面量  →  证据图 G（每个节点带 span）   │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 1  候选 clause 生成（LLM 只在受控词表上做选择）              │
│   输入：证据图的候选边（不是原始代码全文）                        │
│   输出：clause JSON，每条必须绑定 span                            │
│   门控：span validator + 类型检查 + 「至少一个端点证据 +          │
│         一个资源/检查证据」双证据要求                             │
│   未通过 → 记为 unknown，不得编译为告警                           │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 2  状态搭建（确定性，RESTler 式 producer-consumer）          │
│   从创建—读取—修改—删除依赖图，为每个账户用合法端点创建同型资源   │
│   state-unreachable 是**被报告的指标**，不是静默跳过              │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 3  多账户差分判定（本方案的核心）                            │
│   对照组：① 攻击者访问自有对象 → 成功签名 S_self                │
│           ② 攻击者访问幽灵对象 → 拒绝签名 R_ghost               │
│           ③ 重复执行 → 稳定性                                    │
│   被测：  ④ 攻击者访问受害者对象                                │
│   分层 verdict（不是单一布尔）：                                  │
│     confirmed-read  /  confirmed-write  /  likely  /  inconclusive│
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 三处最脆弱的环节 + 替代设计

批判审查指出了 v1 的三个致命弱点，逐一替换：

**弱点 A：让 LLM 直接从散落制品输出完整契约。**
这恰好落在 LLM 的已知失效区——隐含缺失约束、循环/状态依赖、语义等价变换会产生"连贯但不真实"的解释[Lec25][Wan26]。

→ **替代：证据先行的两层 IR。**
第一层完全确定性抽取（endpoint / 路由 / middleware / ORM ownership 字段 / SQL predicate / role 字面量 + span）；
LLM 只能在该证据图的候选边上做受控选择，输出 JSON Schema；
第二层 clause 必须过 span validator、类型检查、"双证据"门控。无法证明的 relation 记 `unknown`，
**不得编译为越权告警**，只能作为人工审计线索。

**弱点 B：三重对照的"成功签名相等"规则过度简化。**
`Test == self-success` 会漏掉"返回了受害者数据但字段顺序/时间戳/分页不同"的真实 BOLA；
`Test != ghost-rejection` 也不必然说明越权。

→ **替代：分层 verdict，而非单一布尔。**

| verdict | 判定条件 | 是否计入主指标 |
|---|---|---|
| `confirmed-read` | Test 响应中出现受害者对象的稳定唯一字段，或能用攻击者会话读回受害者状态 | ✅ |
| `confirmed-write` | Test 触发可回读的受害者对象状态改变 | ✅ |
| `likely` | 成功 schema 与合法基线一致，但不能证实归属 | ❌ 单列 |
| `inconclusive` | 对照不稳定 / 异步未完成 / 对象不存在性不确定 / 响应不可解析 | ❌ 单列 |

**弱点 C：把状态前置条件交给 LLM 反推。**
这是把方法最难的 planner 交给最不可靠的模块，且与 BACFuzz 已承认的复杂状态盲区重合[Dha25]。

→ **替代：以 API producer-consumer 图做确定性状态搭建**[Atl19]。
先由 OpenAPI/运行时日志建立创建—读取—修改—删除依赖图；
对每个账户用合法 producer 端点创建同型资源；
只把**无法满足**的路径条件作为 LLM 的局部解释候选，不允许其生成任意测试状态。

### 3.3 形式化 sketch

设应用 A，身份集合 I（≥2 个真实账户），资源类型 T。
对三元组 (endpoint e, 身份 i, 资源实例 o) 定义：

- `S_self(e, i)`：i 访问**自己创建**的 o 的响应签名（规范化后）
- `R_ghost(e, i)`：i 访问**不存在的** o′ 的响应签名
- `Resp(e, i, o)`：待测请求的响应签名

BOLA-oracle 定义为分段函数：

```
verdict(e, i, o_A) =
  confirmed-read   if  ∃ 稳定唯一字段 f ∈ Resp 使 f ∈ OwnerFields(o_A)
                       且 f ∉ R_ghost 的字段集
                       且 重复 k 次一致
  confirmed-write  if  可回读的 o_A 状态发生改变
  likely           if  Resp ≡ S_self  且  上述归属条件不成立
  inconclusive     otherwise / 对照不稳定
```

其中 `OwnerFields` 由阶段 0 的证据图给出（ORM 归属字段 + SQL WHERE 上的 owner 列），
**不是由 LLM 猜的**。这是本方案把"对象归属"从主观判断变成可机检量的关键。

## 4. 实验设计

### 4.1 数据集分层（诚实标注）

材料里**没有**任何一篇证明 crAPI / VAmPI / DVGA / Juice Beverage / PetClinic 的漏洞清单完整或可直接当评测集。
因此分层如下，未证实的一律写"待核对"：

| 层级 | 内容 | 用途 | 状态 |
|---|---|---|---|
| L1 最小可复现层 | crAPI、VAmPI 等公开靶场 | 功能回归 + 可重复 PoC | 靶场存在，**BOLA/BFLA 清单待核对** |
| L2 构造式真值层（自建 benchmark） | 选少量可容器化 API；每个缺陷绑定一个修复版/安全孪生端点；发布 version pin、diff、账户创建脚本、资源 ID 映射、期望 verdict | 主实验（precision/recall/FPR 可控） | 自建 |
| L3 现实性层 | 仅纳入**能独立复现且有公开修复证据**的 CVE / 已确认缺陷 | 现实性验证 | 缺证据的写"未验证"，不把 CVE 标题当真值 |
| L4 阴性层 | ≥1 个未注入的正常业务 API；安全孪生与修复版视为第一类阴性 | FPR 测量 | — |

> **为什么必须有 L2**：Cro23 显示真实漏洞数据集 20–71% 的标签可能不准确、17–99% 的数据点可能重复。
> 构造式真值是优势，**但不等于现实性证明**——所以 L3 不能省，且 L2/L3 **分开报告，不得合并成一个总分**。

### 4.2 baseline 优先级

| 优先级 | baseline | 原因与边界 |
|---|---|---|
| 必做 | 朴素双账户 ID/字段替换 | 量化校准 oracle 的最小对照，实现完全可控 |
| 必做 | 三个消融：去 clause / 去幽灵对照 / 去稳定性门 | 把"每个设计到底贡献了多少"拆开 |
| 强烈建议 | BACFuzz[Dha25] | 最接近的工程竞品（LLM + SQL oracle）；PHP 可运行性决定能否公平比较 |
| 强烈建议 | EvoMaster 安全 oracle[3] | REST/API 安全测试的最接近公开路线；WFD 语料获取前不得承诺数值比较 |
| 建议 | BolaRay[Hua24] | 静态 BOLA 上界/下界；仅 PHP、忽略 SELECT，须在共同对象集上报告 |
| 建议 | RESTler[Atl19] | 作为状态构建/探索底座，**不是**完整的越权 oracle baseline |
| 可选 | BACScan[Liu25b]、A2CT[Sch25] | 源码/运行环境可得时比较；否则仅作相关工作 |
| **不宜作主 baseline** | Udd26、NeO[Li26g]、ACBreaker[Wan25d] | 任务域分别是微服务策略漂移 / 跨服务权限提升 / IoT 接口绕过。**详细比较设计，不伪造端到端数值比较** |

### 4.3 预注册成功标准（替代 v1 那个没有依据的 FPR<10%）

实验开始前冻结以下标准，避免事后挑选：

1. 与朴素 ID 替换相比，**相同请求预算**下 precision 显著提升，且 recall 不出现大幅牺牲；
2. 在安全孪生端点、修复版本、≥1 个正常业务应用上报告 **FPR 与置信区间**；
3. 每个 TP 都有：重放脚本 + 攻击者/受害者对象创建记录 + 三组对照响应 + 最小化 PoC；
4. LLM clause **单独报告**：syntax validity、evidence-span validity、与专家/代码真值的一致性——**不能只报端到端 F1**；
5. 与 ≥1 个最强可运行基线 + ≥1 个强消融做 **paired 比较**（按应用配对，不汇总请求数）。

| # | 消融 | 想回答的问题 | 预期（待验证） |
|---|---|---|---|
| 1 | 去掉 clause（改用通用 BOLA 模板） | clause 归纳到底有没有用 | — |
| 2 | 去掉幽灵对象对照 | 误报是不是靠对照压下去的 | FPR 应显著上升 |

| 5 | 单账户 vs 双账户 | 差分本身的价值 | — |

| 风险 | 严重度 | 应对 |

| 审稿人：「与 Udd26 / BACFuzz 重合」 | 高 | 第 2 节列逐组件差异表；尽量复现比较可获得部分；若不可比，**明确承认不可比**并把贡献限定为 calibrated ownership oracle |

## 7. 与 v1 的差异一览

| 维度 | v1 (AuthOracle) | v2 |
|---|---|---|
| 主线命题 | LLM 归纳授权契约 + 三重差分证伪 | **Evidence-grounded, state-calibrated oracle for BOLA detection** |
| LLM 角色 | 假设生成器 | **受控 candidate ranker**（可降级为可选排序器） |
| 首创声明 | 隐含"首个 LLM×API 授权" | **全部撤回**，改为"待验证的对象归属校准组合" |
| 对照机制 | 三重阴性对照 | 三层对照 + **分层 verdict**（confirmed-read/write、likely、inconclusive） |
| 状态搭建 | LLM 反推 | **确定性 producer-consumer 图** |
| 成功标准 | FPR<10%（无依据） | **预注册 5 条**（提升 precision、报告 FPR 置信区间、可重放 PoC、clause 单独评测、paired 比较） |
| 数据集 | crAPI/VAmPI 等直接当评测集 | **L1–L4 分层**，未证实的一律标"待核对" |
| 竞品处理 | 未识别主要竞品 | **逐项差异表**对 Udd26 / BACFuzz / ACBreaker / BolaRay / NeO / BACScan / EvoMaster |

## 8. 下一步（按性价比排序）

1. **动机实验**（成本最低、立论最硬）：统计几个真实开源 API 里，授权规则有多大比例**在 OpenAPI 中表达不出来**，
   以及有多大比例的 BOLA 需要跨制品证据才能发现。用硬数字钉死"规格不足以表达授权"。
2. **确认可获取的 baseline**：BACFuzz 与 EvoMaster 安全 oracle 的代码/语料是否能拿到——
   **这决定论文能不能做公平比较，直接决定方案可行性**。
3. **核对 L1 靶场的真实漏洞清单**：crAPI / VAmPI 的 BOLA/BFLA 清单是否存在官方版本，不能靠猜。
4. **搭 L2 benchmark 的最小子集**：1 个应用 + 3 个注入缺陷 + 对应修复版，先跑通全链路。
5. 若 (2) 显示 BACFuzz / EvoMaster 都拿不到，则把论文重新定位为「**状态化 BOLA oracle 与基准**」，
   而不是"比 SOTA 更好的检测器"。
