# Artifact release checklist (for JISA reproducibility)

This document lists everything a third party needs to **reproduce every number
and table in the paper** and to **re-run the experiments**. It is the companion
to `reproduce.sh`.

> Status: the seeded positive-control experiment has been **run** (see §4);
> its inputs, scripts and JSON output are part of this artifact. GitHub
> publication awaits repository creation (see §5).

- **Analysis pipeline** (`04_绘图与分析/analysis/`): `compute_all.py`,
  `ingest_native_engine.py`, `ingest_gogs.py`, `ingest_gitlab.py`,
  `ingest_seeded.py`, `make_diagrams.py`, `normalize_bib.py`,
  `check_macros.py`.
- **Raw records** (`04_绘图与分析/results/*.json`,
  `experiments/real_system/results/*.json`): the factorial study, the Gitea /
  Gogs / GitLab cell grids, the native-engine execution log, the M1 census,
  and the seeded positive-control record (`seeded.json`).
  These are the inputs `compute_all.py` and the ingest scripts consume.
- **Per-table auto-generation scripts** (the ingest/compute scripts above)
  so every entry of Table 2–11 is traceable to a line of code.
- **Scenario configuration**: the design-cell definition (52 cells × 2 MRs × 3
  exception policies × 2 reachability readings) and the `m1_census.py` /
  `m1_gitea_swagger.py` route tables.
- **Deployment configuration** for the three real systems:
  - Gitea `1.22.6` (docker image digest to be recorded),
  - Gogs `0.14.3` (single static binary; exact build/version),
  - GitLab `17.11.7` (Docker image digest to be recorded; `gitlab_lab/bootstrap.md`
    records the one-time rails-runner PAT bootstrap).
- **Environment**: OS, JDK and Maven versions used for the native-engine run,
  Python `3.13.12`, and the `matplotlib`/`pandas` (no `scipy`) setup. The
  diagram step additionally needs `svglib` + `reportlab` (SVG -> PDF);
  `reproduce.sh` auto-detects an interpreter that provides them.
- **Raw logs**: the engine's own `getFailures()` output and the per-cell probe
  logs; each record carries a unique ID, its expected output, and a
  SHA-256 checksum.
- **`build.sh`** and the LaTeX source (`03_论文撰写/paper/`) to regenerate
  `main.pdf` from the generated `*.tex` numbers.

## 2. Reproduce (no re-run needed)

```bash
bash reproduce.sh
```

This regenerates `results/*.tex` from the shipped raw records and then builds
`main.pdf`. Every scalar in the paper is emitted by `compute_all.py`; nothing
is hand-typed in the body.

## 3. Re-run the experiments

The real-system labs live under `experiments/real_system/`: `gitea_lab.py`,

## 4. Positive control with a seeded vulnerability (run 2026-09-19)

To answer the reviewer's "why are all three real systems non-vulnerable?" —
and its dual, "when a real object-level flaw is present, does the detector
find it?" — we ran a **positive control** (paper §5.9, Table 11).

**Design.** Patching the Gitea binary was infeasible on this host (no
Go/MinGW toolchain), so the control uses a *controlled authorization target*
(`experiments/real_system/seeded_target.py`): an in-process HTTP server that
faithfully emulates the Gitea 1.22.6 object-level authorization API contract
the engine actually consumes (same endpoints and fields probed above), backed
by a *correct* internal authorization model, with **3 deterministically
seeded vulnerable instances** (3 cases of one fault pattern: none-entitlement
subjects served the object at `GET /api/v1/repos/{owner}/{repo}`; they differ
in subject and object, not in fault location) and **1 seeded BFLA defect**
(non-privileged actor succeeds at `PUT .../collaborators/{u}`).
The ground truth of which cells are vulnerable comes from the seed list, not
from the detector.

**Harness.** `run_seeded.py` drives the target with the *same* topology,
mutation, crawl, introspection and four-method adjudication code paths as
`run_real.py`, differing only in the system under test.

**Result** (`experiments/real_system/results/seeded.json`; Table 11,
regenerated by `analysis/ingest_seeded.py` → `results/seeded_table.tex`):

| method | TP | FN | FP | TN |
|---|---|---|---|---|
| mr_bookkeeping | 3 | 0 | 2 | 43 |
| v3 (owner vantage) | 3 | 0 | 0 | 45 |
| v3 (subject vantage) | 3 | 0 | 0 | 45 |
| direct_only | 3 | 0 | **30** | 15 |
| direct_observe | 3 | 0 | 0 | 45 |
| direct_observe (subject) | 3 | 0 | 0 | 45 |

The observation-gated adjudicator catches **all 3 seeded defects with zero
false positives** (TP=3, FN=0, FP=0); the strawman `direct_only` again
over-claims (FP=30). The read-oriented engine does not cover the seeded BFLA
(write-oriented) defect — reported in §5.9 as an honesty boundary, not a
detection failure.

**Scope caveat (stated in the paper).** This is a controlled research
artefact, not production Gitea; it validates that the detector's logic fires
on a genuine broken object-level check and stays silent elsewhere. It does
not claim to discover Gitea's real CVEs.

**Re-run:** `python experiments/real_system/run_seeded.py` (stdlib only, no
external services), then `python 04_绘图与分析/analysis/ingest_seeded.py`.

## 5. GitHub publication

The repository layout follows §1. Publication steps: create the repo,
`git init && git add && git commit`, tag the release commit, and push. The
commit hash, the raw JSON records and their SHA-256 checksums (§1) must be
recorded in the camera-ready's artifact footnote. `gh` CLI / a push token was
not available on the build host at artifact-freeze time, so the push itself
is performed by the corresponding author.
