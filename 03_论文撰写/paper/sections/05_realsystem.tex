\section{Real systems: Gitea, Gogs, GitLab, and a seeded control}
\label{sec:realsystem}

We repeated the essential comparison on real systems, choosing Gitea \ResRsVersion{} for
object-level sharing with per-object visibility, a machine-readable sharing surface, and a
documented administrative grant path. Gitea enforced the expected decisions on the endpoints
exercised here, so the experiment measures the false-proof side; the reachability model is
reported under \emph{both} readings---crawl-time snapshot and live execution-time
state---so the reading moment is the explanatory variable. The experiment produces
\ResRsCells{} cells, \ResRsCellsSnapshot{} per reading.

\subsection{Eight committed transitions with a frozen model, on two products}
\label{sec:temporal}

We ran eight authorisation transitions on one fresh Gitea \TmpVersion{} instance and repeated
the same eight, under the same frozen protocol (hash \texttt{\TmpProtocol}) and ledger rules,
on an independent GitLab CE \TmpGVersion{} instance. The mechanisms differ per product, so the
two runs share a protocol, not a topology, and we report them side by side rather than pooled.

Each transition is a closed loop: crawl every subject, serialise the per-subject reachable
set, freeze it as $M_0$ and record its digest; commit one authorisation transaction; re-crawl
with the \emph{same} credentials to obtain $M_1$; read the oracle from the owner vantage;
issue the request and verify the effect by content; classify against the ledger at decision
time. All \TmpBothPolicyEvents{} transactions committed, all \TmpBothMzeroVerified{} frozen
$M_0$ digests were unchanged when re-checked immediately before probing, and all
\TmpBothVersionConsistent{} cycles were version-consistent, over \TmpCalChecks{} gate checks
(\TmpGCalGateChecks{} on GitLab). Across \TmpBothCells{} cross-credential cells
(\TmpCells{} on Gitea plus \TmpGCells{} on GitLab), $E$ and $Y$ agree in \TmpBothEeqY{} cases
(\TmpGEeqY{} of the GitLab cells) under the closed-world default reading;
Table~\ref{tab:unknown-sensitivity} reconciles this with the literal \emph{unknown} rule,
under which the scorable set is the \TmpBothLitKnown{} $E$-allow cells and the agreement is
\TmpBothLitEeqY/\TmpBothLitKnown{}.

The stale model produces \TmpBothStaleFP{} false proofs (\TmpStaleFP{} on Gitea, \TmpGStaleFP{}
on GitLab), and a recrawl with the same credential removes \TmpBothFixed{} of them, leaving
\TmpBothStillMiss{} still missed and \TmpBothLiveFP{} live false proofs
(Table~\ref{tab:temporal}). The composition is informative rather than uniform, and the two
products agree on its shape: one cell for the direct grant, one for the inherited-channel
attachment, five and six when a repository becomes public, and six and eight when a user
becomes site administrator---the cases a single-object probe is least likely to anticipate,
because the granting event is not about the object. Revocations must not be scored as misses:
the old model still lists \TmpBothOverRevoke{} cells whose access was revoked
(\TmpOverRevoke{} on Gitea, \TmpGOverRevoke{} on GitLab), and in every one the request is
refused.

The multi-channel transition is where the products part company: on Gitea, after the team
member is removed, \texttt{acme/t1} remains readable through a direct collaboration while
\texttt{acme/t2} becomes unreadable, and the ledger records the remaining channel. On GitLab
removing a member from a group also deletes that user's project-level membership, so we
placed the alternative channel on a personal project and record the cascade as a
product-semantics observation rather than a ledger rule (amendment A2).

The oracle column separates the products more sharply than the transition counts. On Gitea
the owner vantage answers \TmpOracleReadable{} of \TmpCells{} cells (the rest are anonymous),
but the subject's own vantage answers only \TmpOracleSelfReadable{}---all after the
site-admin grant. On GitLab the owner vantage answers \TmpGOracleReadable{} of \TmpGCells{},
and the subject's own credential answers \TmpGOracleSelfReadable{}, because GitLab's member
endpoint is readable by any project member. That readability is not soundness: the endpoint
answers ``is this principal a member'', so it returns 404 for a public project a non-member
may read and for a site administrator who may read everything. Measured against the ledger,
the Gitea oracle disagrees on \TmpOracleDisagree{} cells and the GitLab oracle on
\TmpGOracleDisagree{}, all of the latter in the public (\TmpGOracleDisagreePublic{}) or
site-administrator (\TmpGOracleDisagreeAdmin{}) channel.

Table~\ref{tab:oracle-channel} assigns each cell to exactly one channel, by the strongest
channel that grants it; Table~\ref{tab:gogs-channel} gives the same decomposition for Gogs,
because a channel label is a property of the entitlement ledger, never of a probe response.
Both tabulated products answer every direct-collaborator and group cell correctly, and Gitea
also answers its public and site-administrator cells correctly. GitLab errs only by omission,
on the two channels that are not membership, and never returns a false allow; a one-sided
error is enough to manufacture a false proof.

Two properties of the run are what an external check can verify. The protocol was frozen

designed set, so none of the counts is a field rate.

\paragraph{What a recrawl repairs, and what it cannot}
The \TmpBothFixed{} repairs are not a general remedy, because a grant can be absent from the
model for two causes. \emph{Staleness}: the grant is visible through the subject's own
interface, was made after the snapshot was frozen, and a fresh crawl with the same credential
lists it again. \emph{Coverage}: the grant is real and enforced, but the enumeration the crawl
runs does not return the object, because the view that would return it belongs to another
subject or to an administrative interface. Recrawling cannot repair a channel the crawl has no
way to enumerate, and the cross-vendor run locates the residue: on Gogs \GgMismatchLive{} of
\GgMismatchSnap{} mismatching cells survive the live reading---\GgLiveMismatchPublic{} on
public visibility and \GgLiveMismatchSiteAdmin{} on the site-administrator vantage---and
\GgFpBookkeepingLive{} of \GgFpBookkeeping{} bookkeeping false proofs survive, all
\GgLiveFpPublic{} of them on public visibility. No team-derived or collaborator grant
survives, because this product resolves team inheritance in the subject's own list. The live
reading removes the staleness term and leaves the coverage term; where the same channels are
represented in the subject's crawl, as on Gitea and GitLab, the live reading reaches zero.

That attribution is measured, not subtracted: in one instance, with the same subject,
operation, surface and budget, and every grant made after the snapshot by another account,
three channels ran in parallel---direct collaborator, team-derived, public repository
(\RfArms{} arms, \RfSnapAlarms{} alarms). The recrawl repaired \RfRepaired{}: the collaborator
and team objects appear in the subject's list on the second pass. It left \RfPersisting{}:
the public repository, readable in the same probe as the other two but not returned by the
enumeration the recrawl runs---the subject's own repository list, the organisation list, and
the first page of an unfiltered search. A query that names that repository does return it
(\RfNameFound{} hit), so the boundary is the enumeration's page and filter rather than the
system's visibility rules. What generalises is the mechanism rather than the ratio: a recrawl
repairs exactly those grants whose granting channel the renewed crawl can enumerate.

\subsection{Cross-vendor replication of the snapshot design: Gogs \GgVersion{} and GitLab \GlVersion{}}
\label{sec:gogs}

We repeated the same three-phase protocol and \ResRsCellsSnapshot{}-cell design on two further
systems (Table~\ref{tab:gogs-cross}): \textbf{Gogs} \GgVersion{}, the project Gitea forked from
in 2016 (census from its pinned route table, \GgRoutePaths{} paths), and \textbf{GitLab}
\GlVersion{} (census from the pinned running instance's routes, \GlRoutePaths{} paths, since
its OpenAPI document omits core grant endpoints).

\input{gogs_cross_table}

The replication introduces a primary methodological variation: the authorization-introspection
surface, which shows that \emph{readability does not imply soundness}. Gitea's owner-vantage
surface is readable and sound (agrees with effective access on all \GtOracleAgree{} cells).
Gogs's collaborator-membership endpoint is equally readable (\GgOracleReadable{}/\GgCells{})
but unsound---wrong on \GgOracleWrong{} cells (\GgOracleWrongPct\%), exactly the authorizations
arising outside direct membership: site administration (\GgFnSiteAdmin{}), public visibility
(\GgFnPublic{}), out-of-band grants (\GgFnOob{}). GitLab's \texttt{members/all/\{u\}} resolves
inherited membership, but public visibility and site administration confer none:
\GlOracleWrong{} false negatives (\GlOracleWrongPct\%). What a surface cannot see is
predictable from what it measures---why clause~(2) of the admissibility condition cannot be
automated from readability alone.

Table~\ref{tab:gogs-channel} locates those \GgOracleWrong{} errors on the ledger axis.
Panel~(a) groups the \GgChCells{} cells by granting channel: the surface is correct on all
\GgChCollaboratorAgree{} of the \GgChCollaborator{} direct-collaborator cells and all
\GgChNone{} cells with no recorded grant, answers \emph{deny} on all \GgChFalseDeny{} cells
entitled through team membership (\GgChTeamFalseDeny{}), public visibility
(\GgChPublicFalseDeny{}) or site administration (\GgChSiteAdminFalseDeny{}), and never answers
allow where the ledger denies (\GgChFalseAllow{}). Panel~(b) re-groups the same cells by
mechanism: \GgChSrcTeam{}, \GgChSrcPublic{} and \GgChSrcSiteAdmin{} cells, all wrong, against
\GgChSrcCollaborator{} and \GgChSrcNone{}, all right. The blind spot belongs to the chosen
surface, not to the API: the per-object permission suffix returns \GgChProbePermSuffix{}, the
per-object team route \GgChProbeTeamMember{} and the collaboration route the oracle consults
\GgChProbeCollabGet{}, while the organisation team listing is reachable
(\GgChProbeOrgTeams{}) but is not a per-object authorization surface. The live reading gives
\GgChLiveAgree{} agreements and \GgChLiveFalseDeny{} false denials. \GgChMultiBasis{} cell
carries two ledger rules and is counted once under the stronger rule, so the rows sum to
\GgChCells{} cells rather than the \GgChRules{} recorded rules.

The consequence is measurable: on Gitea the surface-gated adjudicators produced no false
proofs (\GtFpVthree{} v3, \GtFpDirectObserve{} direct-observe), while on Gogs they manufacture
them (\GgFpVthree{} snapshot, \GgFpVthreeLive{} live, \GgFpDirectObserve{} direct-observe) and
on GitLab again (\GlFpVthree{}, \GlFpDirectObserve{}), every v3 false proof falling on a cell
whose authorization derives from site administration or public visibility
(\GgImplicitSiteAdmin{} and \GgImplicitPublic{} such cells on Gogs; \GlImplicitSiteAdmin{} and
\GlImplicitPublic{} on GitLab). No admissible oracle was available from the tested surfaces on
Gogs or GitLab, so the honest adjudicator abstains where those surfaces would license a
promotion.

Bookkeeping alarms false-proof on legitimately granted access on every product (Gitea
\GtFpBookkeeping{}, Gogs \GgFpBookkeeping{}, GitLab \GlFpBookkeeping{} cells) with the same
out-of-band-dominant grant profile, and the reachability mismatch persists on all three (Gitea
\GtMismatchSnap{}, Gogs \GgMismatchSnap{}, GitLab \GlMismatchSnap{} snapshot). On Gogs the
mismatch only partially resolves live (\GgMismatchLive{} remain); on GitLab the live reading
recovers everything (\GlMismatchLive{} remain)---a second, vendor-specific failure of the
snapshot premise, in the crawl model rather than the oracle.

\subsection{A seeded positive control}
\label{sec:seeded}

The three real systems enforce the expected decisions, so the question remains: \emph{when a
real object-level flaw is present, does the same detector find it?} A \emph{controlled
authorization target} emulates the Gitea API contract the engine consumes, with a correct
internal authorization model and \SeedBolaN{} seeded vulnerable instances, all instantiating
one fault pattern (a none-entitlement subject served the object at
\texttt{GET /api/v1/repos/\{owner\}/\{repo\}}), differing in subject and object, not in fault
location. Its introspection surface reports the \emph{correct} \texttt{none} permission, so
the defect is visible only as a discrepancy between oracle and request. We drove it with the
same topology, mutation, crawl, introspection and adjudication code as above; ground truth
comes from the seed list.

\subsection{Four defect classes on the controlled target}
\label{sec:multiclass}

We seed four classes on the same target---the read bypass already in use with three
instances, plus two instances each of three new classes. C1 is the read bypass. C2 is a write
bypass: a subject whose true permission is \texttt{none} changes the object's metadata with
\texttt{PATCH}. C3 is a faulty inheritance expansion: a member outside the team is served the
team's repository, and the listing, the search results and the object read all agree that the
subject may see it. C4 is an escalation: a subject that is neither owner nor administrator
grants a third party access it should not have.

\input{multiclass_table.tex}

Table~\ref{tab:multiclass} reports per-class recall against the seeded truth and, separately,
false alarms on authorized cells of the same channel. C1 is the only class the read relation
covers. C2 breaks a different channel: the relation asks whether the object is \emph{served},
not whether it can be \emph{changed}, so it is silent on both instances; moving the same
relation to the channel the defect breaks recovers both. C3 and C4 are undetected end to end,
because in both the subject already sees the object, so \texttt{cannotReachThroughGUI} is
false and the antecedent does not hold. They stay in the
denominator---\McChannelHits{} of \McInstances{} for the channel-matched relation---and the
antecedent's failure is the explanation, not an exclusion.

The oracle-consuming adjudicator fires on all \McInstances{} instances once the probe is
channel-matched, and on \McOracleReadHits{} of \McInstances{} when confined to the read
channel. False alarms are counted per channel, because a read cell cannot stand in for a write
or a grant: \McNegRead{} read cells, \McNegWrite{} write cells and \McNegGrant{} grant cells.
The relation's bookkeeping variant alarms on \McFpRelRead{} of \McNegRead{}, \McFpRelWrite{}
of \McNegWrite{} and \McFpRelGrant{} of \McNegGrant{}, and the oracle-based adjudicator on
\McFpOracleMax{} of each. Write success is judged by the object's state changing, not by the
status code. The oracle answers these recorded cases correctly, which is soundness on this
target, not independence. The leave-one-out is reported per method: on the channel-matched
adjudicator, disabling a class's fault removes that class's alarms and leaves the others in
place, for all \McLooAdjudicatorClasses{} classes; the read relation provides the same
evidence for \McLooReadClasses{} class and the channel-matched relation for
\McLooChannelClasses{}.

\subsection{A publicly fixed defect}
\label{sec:cvepair}

We also ran one defect nobody here planted: Gitea \CveVulnVersion{} against \CveFixedVersion{},
the release whose notes record a security fix titled ``Fix comment permissions''
(\texttt{\#28213}, backported as \texttt{\#28216}); the same defect is catalogued as
CVE-2023-49946 for Forgejo. What is missing is object ownership rather than path permission: a
caller entitled to the repository named in the URL can address an object belonging to a
different, private repository. Each version runs as a fresh instance: alice owns a private
repository with one issue comment, bob owns a public one, and bob sends \texttt{PATCH\allowbreak
/api\allowbreak/v1\allowbreak/repos\allowbreak/bob\allowbreak/pub\allowbreak/issues\allowbreak/comments/\allowbreak\{alice's comment id\}}
with a replacement body. On \CveVulnVersion{} the write succeeds (HTTP \CveVulnStatus{}) and
alice's own re-read returns the replacement body, so the effect is real and not a status-code
artifact; on \CveFixedVersion{} the same request is refused (HTTP \CveFixedStatus{}) and
alice's re-read is unchanged (Table~\ref{tab:cvepair}). The ledger gives bob no write channel
on alice's repository ($E$ = deny), so the vulnerable cell is a true positive and the fixed
cell raises no alarm: \CveTruePositives{} true positive and \CveFalseProofs{} false proofs
across the pair. All \CveControls{} control writes behave as expected in both versions, and
alice's restore returns the body to the original in \CveRestored{} of \CveVersions{} instances.

The relation is not executed on this pair, so the alarm recorded here is the $E/Y$ gate's own
verdict: the result measures the gate, not the relations' recall on a real defect, and it
shows the gate issuing a correct violation claim and ceasing to issue it once the vendor fixes
the defect.
