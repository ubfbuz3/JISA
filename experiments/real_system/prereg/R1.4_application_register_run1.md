## Verdict pattern, stated plainly

Every row is `reject`, but not for one reason: row 5 fails clause (1) (the oracle
cannot be read at all); rows 1–4 are `conservative-L1` refusals with no source
audit; rows 6–10 are `shared` at L2 on grounds that differ by class — a shared
function (6), shared authorization state with a duplicated rule (7), a fault
placed where the oracle does not read it but the same class of fault could
propagate (8), and shared state whose correctness depends on a flag written by the
path under test (9). The rule was not used to launder a convenient answer: no row
would become `admit` if the wording were stretched, and no row was re-decided
after its run.

## What this changes in the paper

Nothing numeric. Every number obtained under a `reject` row is a **diagnostic
reading**, not a confirmed violation, and the manuscript reports the
controlled-target results against constructive truth rather than as discoveries.

The consequence that matters for R1.9: the oracle-based adjudicator reaches all
nine seeded instances (Table 17), but on a target whose oracle the frozen rule
classifies `reject`. The nine hits are therefore recall **against known truth**,
measured to answer "does the chain fire", and they are explicitly *not* offered
as independence-certified proofs.

## Rows that could have gone the other way

- If the emulator had implemented the oracle as a separate service with its own
  copy of the grant tables, rule 4 would have fired and rows 6–9 would read
  `admit` at L2. It does not, and we did not restructure it after the fact to
  make the rule return a more flattering answer.
- If Gitea's source had been audited below the server boundary, rows 1–3 could
  have moved to L2 under rule 4 or stayed `reject` under rule 2. We did not
  perform that audit, so the level stays L1 and the reason stays
  `conservative-L1`.

## Falsification checks performed

- §7 bullet 1: no `reject` row was re-decided, because no L2 evidence

- §7 bullet 2: no `admit` row exists, so no L3 falsification was applicable.
- §7 bullet 3: every `pending` row from the frozen register is resolved here by

## Change log

**rev 2 — 2026-10-19.** Re-read `seeded_target.py` against rows 5–8 of rev 1 and
corrected three factual errors in the *evidence*, not in the verdicts:

1. Write-path evidence (now row 7): rev 1 said the PATCH authorization is
   "`runtime_perm()` plus a bypass set". The handler does not call
   `runtime_perm()`; it uses an inline owner/admin guard plus the `write_bypass`
   clause. The row is re-argued on shared state and a duplicated rule, and says
   explicitly that the bypass is guard-only.
2. Inheritance evidence (now row 8): rev 1 said the oracle and the content path
   "see the same faulty expansion". The oracle calls `intended_perm()`, which
   does not read `inherit_perm`; that is precisely why the oracle reports `none`
   for C3. The row is re-argued on the shared inheritance branch of
   `intended_perm()` and states that non-propagation is a property of fault
   placement.
3. Escalation evidence (now row 9): rev 1 said both paths read "the tainted grant
   set". Only `runtime_perm()` honours the tainted collaborator record;
   `intended_perm()` excludes it via `tainted`. The row is re-argued on shared
   state whose correctness depends on the flag written by the path under test.

Also in rev 2: row 5's Gogs version corrected from 0.13 to 0.14.3 (the version the
archived cross-vendor experiments actually ran), and row 3 added for Gitea 1.22.6,
the build behind the main temporal experiments, which rev 1 left implicit.

The first fill of this register and this revision were both made **after** the
R1.9 and R1.7 runs; the register is an application record, not a pre-registered
object, and this log is the record of its correction.
