## 01-BOLA-BFLA 检测/BOLA BFLA 自动化检测技术全景

现有工作已形成两条互补主线：数据库/源码中心的静态权限推断，以及多身份、状态感知的动态 API 测试；前者更擅长解释“应保护什么”，后者更擅长验证“攻击是否真的成功”，两者的共同瓶颈是授权 oracle 而非请求生成本身 [Hua24, Liu25e, Dha25, Liu25b]。
  
  #### 方法与检测 oracle
  - **静态/白盒**：BolaRay 将 SQL 分析与静态分析结合，推断四类对象授权模型；MOCGuard 和 PCFinder 分别从数据库所有权、权限检查识别缺失检查，已在数十个真实 Java/数据库应用中发现大量经确认漏洞 [Hua24, Liu25e, Shi25]。CanCheck、SPACE 等则将代码暴露路径与声明/隐含策略进行逻辑一致性验证 [Boc16, Nea16]。
  - **黑盒/灰盒**：多身份交换、triad testing 和 owner/non-owner 重放是 BOLA 的主流 oracle；BFLA 则通常依赖低权限身份触发受保护操作，并确认状态改变或业务副作用 [Che25c, Kaw21, BACScan]. 仅比较 401/403/404 或响应相似度并不可靠：这些状态可能表示拒绝、隐藏资源存在性或业务错误。较稳健的设计把正常基线、跨身份响应、敏感字段、操作反馈、数据库/SQL 流和外部副作用联合起来 [Liu25b, Dha25, Sah26]。
  
  #### 规格、搜索与形式化模型
  OpenAPI 可提供端点、参数和 producer–consumer 依赖，但单独只能生成候选攻击面；RESTler、Morest、Nautilus 和 EvoMaster 说明状态序列与反馈引导对深层路径至关重要 [Atl19, Liu22, Den23]。CPN/一阶逻辑/RBAC 模型能给出更强的策略级 oracle，却依赖准确的策略和模型映射，存在 model–reality gap [San25, Xu15, Boc16]。覆盖引导与灰盒方法正将运行时反馈、SQL 证据和语义参数生成合并，例如 BACFuzz 在 20 个真实应用上验证了 17 个已知问题中的 16 个，并发现 26 个新问题 [Dha25]。
  
  #### 证据规模与缺口
  高价值实证已出现：BolaRay 报告 193 个真实漏洞、52 个 CVE [Hua24]；BACScan 报告 89 个漏洞、35 个 CVE [Liu25b]；Azure/Office365 和 Ant Group 生产系统证明了生产级可部署性 [Atl20b, Liu21]。但评测仍高度依赖开源应用、人工构造脆弱 API 和不统一的真值；WFC/WFD（36 个 API）是较具可复现性的基线 [Sah25]。总体上，BOLA 的跨对象验证已较成熟，BFLA、跨服务工作流和可公开复用的策略级基准仍明显不足。

## 02-LLM 授权语义推理/LLM 推断授权与访问控制语义

当前文献的核心结论是：LLM尚未成为从服务端代码直接恢复授权语义的可靠独立方法；最成熟的路线仍是由静态分析、动态探索或数据库分析抽取事实，再由模型解释或生成候选，最后由确定性验证器裁决 [Zha24b, Le21, Hua24, Liu25e, Vat25b]。
  
  #### 已形成的语义恢复基础
  - 非LLM方法已能恢复RBAC、对象所有权、数据库查询过滤、路由权限和ReBAC关系，并用于发现缺失检查或策略不一致 [Boc16, Ber20, Sun11, Iye22]。
  - LLM研究主要充当语义补全层：识别权限相关变量 [Wan24b]、聚合代码语义进行角色工程 [Luo25]、跨服务规划分析 [Li26g]，或辅助智能合约权限漏洞检测与修复 [Lin25b, Zha24e]；直接从源码稳定提取租户边界、业务所有权和隐含拒绝条件的证据仍少。
  
  #### 可靠性边界与工程模式
  复杂循环、缺失守卫、多步骤工作流和仓库级上下文会诱发连贯但与真实语义不符的解释；模型对语义等价变换也不稳定 [Lec25, Wan26, Ma24b, Jin25]。ABAC策略挖掘还表现出规模下降和过授权 [Bui26, Bab25]。有效系统普遍将LLM限制为候选生成或语义分类，并以代码图、污点/数据流、执行轨迹、SMT/符号执行或差分测试提供可复核证据 [Wen24, Li24f, Hal25, Dha25, Lu26]。规范与不变量推断的结果同样支持这一边界：可验证的候选生成可行，但不能把模型叙述当作最终判定 [SpecGen/AutoSpec: Ma24, Wen24; FormalBench: Lec25]。

## 03-Oracle 与差分测试/Security Oracle 与差分测试

现有研究最接近“安全 Oracle + 差分测试”的路线，是在多个受控身份下重放同一请求，并把“跨身份读取/修改成功”与真实对象归属、业务副作用和拒绝信号联合判定，而不是依赖单一 HTTP 状态码或响应相似度 [Arc25, Sah26, Che25c, Liu25b]。
  
  #### 可复用的 Oracle 设计
  - **差分层**：版本/实现间差异测试已系统处理响应归一化、乱序和非确定性 [God20b]；Metamorphic Testing 则以输入变换后的必要关系规避预期输出未知的问题 [Mai19, Cha22, Seg18]。这为“合法请求 → 跨用户变体 → 所有权基线请求”的三元 Oracle 提供了直接范式。
  - **授权层**：三账户 triad testing [Kaw21]、双账户标识符交换 [Che25c]、以及基于操作反馈而非响应相似度的 BACScan [Liu25b]，共同表明应验证数据/状态变化；灰盒方案还可用 SQL 流或数据库所有权推断增强证据 [Dha25, Hua24, Liu25e]。
  - **误报抑制与可执行证据**：差分结果需经重复执行、缓存/限流噪声过滤和副作用确认；生成可执行 PoC 是更强的最终裁决，相关工作已从模型检查攻击序列 [Mar08]、自动 exploit 生成 [Alh18] 延伸到反馈驱动 PoV 测试 [Nit25]。
  
  #### Ground truth 与评估
  合法 API 调用构造的 owner/non-owner 关系比人工标签更接近可验证事实 [Bar26, Che25c]；人工或提交信息标签存在系统性错误，真实漏洞数据集可有 20–71% 错误标签 [Cro23]，并会显著扭曲模型结论 [Nie23, Yad24]。
