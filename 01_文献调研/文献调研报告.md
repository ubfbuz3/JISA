## 1. 领域地图

### A. API 越权检测与防御

解决 REST API 中的对象级授权失效（BOLA）——攻击者篡改资源 ID 后读取、修改或删除他人对象。

- [1] 从零信任与静态污点分析出发，跟踪 resource ID 的生产、传播与消费，推断授权边界并防御 BOLA。
- [2] 将 OpenAPI 转换为彩色 Petri 网，结合 Web 服务器日志做形式化分析与 BOLA 风险检测。

**与其他簇的关系**：该簇聚焦「授权语义是否正确」，而 API fuzzing 簇关注「如何高效触发并验证安全缺陷」。二者天然互补——前者可为 fuzzing 提供授权 oracle，后者可提供动态攻击证据。

### B. REST API 模糊测试与安全 Oracle

解决 REST API fuzzing 只看 HTTP 500/覆盖率/崩溃，难以发现越权、SQLi、XSS 等逻辑安全问题。

- [3] 在 EvoMaster 上增加访问策略违规、SQL 注入、XSS 等自动化 oracle，并生成可执行测试。
- [4] 用白盒搜索启发式解决 API schema 与 SQL 数据库约束不完整的问题。
- [5] 通过搜索式 mock generation 自动处理被测 API 依赖的外部 Web 服务。

**与其他簇的关系**：可成为 API 越权检测的动态执行底座；也可接入 LLM 生成测试输入、解释漏洞或归纳访问控制策略，但材料中尚未看到这种交叉方案。

### C. LLM/图增强的源码漏洞检测

解决传统深度学习跨项目泛化差、纯文本 LLM 忽略程序结构、结论缺少解释的问题。

- [6] GRACE：代码图结构 + in-context demonstration retrieval。
- [7] DLAP：深度学习预测与 LLM prompting 融合。
- [8] SecureQwen：面向大规模 Python 代码库的长上下文漏洞检测。
- [9] LLMVulExp：检测、定位、成因解释与修复建议一体化。
- [12] VulACLLM：AST/CFG 融合、轻量 LLM、LoRA 与知识蒸馏。
- [13] HyVulDect：GNN 混合语义漏洞挖掘。
- [14] 用 NER 做 Python 漏洞检测与分类。
- [15] AIBugHunter：定位、分类、严重性预测与修复建议的工程工具。

**与其他簇的关系**：该簇大多以函数级、源码级 CWE 检测为目标；API 越权是跨端点、跨用户、跨请求状态的业务逻辑问题，因此**不能直接把一般漏洞检测模型迁移过去**。

### D. LLM 漏洞能力评测与工程化

解决「LLM 是否真的优于传统模型、在哪些漏洞任务上有效、如何部署」的问题。

- [10] 在 Big-Vul 上评估开源 LLM 的检测/评估/定位/描述任务，指出 **LLM 并非在漏洞检测上全面领先**。
- [11] JISA 的 Defendroid：联邦学习 + 区块链 + XAI，面向 Android 漏洞检测。
- [12] 关注轻量部署、压缩与效率收益。
- [15] 以 IDE 工具方式呈现发现与修复能力。

**与其他簇的关系**：为「LLM + API 安全」提供实验设计警示——不能只报告大模型表面准确率，必须与非 LLM 基线比较，并评价误报、可执行性和泛化。

## 2. 逐篇速览

### [1] Rethinking Broken Object Level Authorization Attacks Under Zero Trust Principle
- **要解决的问题**：BOLA 中资源 ID 传播与授权边界不匹配导致的水平越权。
- **核心方法**：BolaZ；静态污点分析识别 resource ID 的生产者/消费者及其传播路径，依据系统授权逻辑自适应调整防御规则。自称首个授权引导（authorization-guided）方法。
- **数据集**：10 个 GitHub 项目；CVE 收集的漏洞。
- **评价指标**：需核对原文。
- **主要结论**：可防御收集到的 CVE，并在野发现 35 个新 BOLA 漏洞。
- **明显局限**：证据主要来自静态分析与 GitHub 项目；运行时身份、复杂业务流程、跨服务调用与误报率需核对原文。

### [2] Automated BOLA attack detection in REST APIs through OpenAPI to colored Petri nets transformation
- **要解决的问题**：自动发现 REST API 中的 BOLA 风险。
- **核心方法**：OpenAPI → 彩色 Petri 网转换，结合 Petri 网分析技术与 Web 服务器日志检测风险；附带自动化工具。
- **数据集**：Web server 日志；具体 API 与规模需核对原文。
- **评价指标**：需核对原文。
- **主要结论**：提供了规格+日志驱动的自动化 BOLA 检测路径。
- **明显局限**：依赖 OpenAPI 描述与日志可得性；规格不完整、日志缺字段、复杂授权策略下的准确性需核对原文。

### [3] Enhancing REST API fuzzing with access policy violation checks and injection attacks
- **要解决的问题**：REST API fuzzer 主要依赖崩溃/HTTP 500，无法有效发现访问策略违规与注入漏洞。
- **核心方法**：为 EvoMaster 增加访问策略违规、SQLi、XSS 等 oracle；fuzzing 后增加「安全测试」阶段；输出 Java/Kotlin/Python/JavaScript 可执行测试用例。
- **数据集**：9 个人工样例、8 个 by-design 脆弱 REST API（黑盒）、WFD 语料 36 个 REST API（白盒），共 52 个 API。
- **评价指标**：需核对原文。
- **主要结论**：安全 oracle 可扩展现有 fuzzing，并产生可执行漏洞测试。
- **明显局限**：BOLA/BFLA 的细粒度覆盖、真实业务 API 占比、oracle 误报率、跨框架泛化均需核对原文。

### [4] Advanced White-Box Heuristics for Search-Based Fuzzing of REST APIs
- **要解决的问题**：黑盒 fuzzing 面对 schema 与数据库约束不完整时难以生成有效请求。
- **核心方法**：面向 EvoMaster 的白盒搜索启发式，利用代码与数据库信息处理 under-specified API schema / SQL 约束。
- **数据集**：EMB 语料 14 个 API + 1 个工业 API。
- **评价指标**：需核对原文。
- **主要结论**：部分 API 上有明显提升。
- **明显局限**：材料只表明「部分 API」提升；对授权逻辑漏洞与安全 oracle 的有效性需核对原文。

### [5] Handling Web Service Interactions in Fuzzing with Search-Based Mock-Generation
- **要解决的问题**：被测系统依赖外部 Web 服务时，fuzzing 难以稳定、完整执行。
- **核心方法**：代码插桩检测外部服务调用与响应解析 → 搜索生成 mock → 通过操纵 DNS 把应用流量导向 mock server。
- **数据集**：需核对原文。
- **评价指标**：需核对原文。
- **主要结论**：能把外部服务交互纳入白盒搜索式 fuzzing。
- **明显局限**：依赖插桩与可重定向网络环境；第三方身份认证、状态一致性、复杂服务语义需核对原文。

### [6] GRACE
- **要解决的问题**：纯文本源码输入的 LLM 漏洞检测忽略语法与语义结构。
- **核心方法**：将代码图结构信息融入 LLM；按语义/词法/句法相似度检索 in-context demonstrations。
- **数据集**：Devign、Reveal、Big-Vul。
- **评价指标**：F1。
- **主要结论**：F1 相比 6 个 SOTA 基线至少提升 **28.65%**。
- **明显局限**：面向通用源码漏洞数据集；是否适用于 API 授权类跨端点逻辑漏洞，材料未提供证据。

### [7] DLAP
- **要解决的问题**：DL 模型泛化与可解释性有限；单纯 prompt 的 LLM 检测性能不足。
- **核心方法**：深度学习模型 + LLM prompting 融合框架。
- **数据集**：材料未给出，需核对原文。
- **评价指标**：材料未给出，需核对原文。
- **主要结论**：优于 role-based / 辅助信息 / CoT / ICL prompts 以及 fine-tuning。
- **明显局限**：缺数据集、任务划分、统计显著性与推理成本信息；API 漏洞适配性需核对原文。

### [8] SecureQwen
- **要解决的问题**：在大型 Python 代码库中识别多种安全威胁。
- **核心方法**：64K 上下文的 decoder-only Transformer，对 14 种 CWE 做检测分类。
- **数据集**：187.5 万函数级代码片段（GitHub + Codeparrot + GPT-4o 合成数据）。
- **评价指标**：F1。
- **主要结论**：不同 CWE 的 F1 为 **84%–99%**。
- **明显局限**：含合成数据，真实世界泛化与数据泄漏风险需重点核对；函数级标签不等于 API 调用链与授权状态。

### [9] Towards Explainable Vulnerability Detection With Large Language Models
- **要解决的问题**：漏洞检测缺少可解释定位与修复建议。
- **核心方法**：LLMVulExp；prompt 生成解释标注 + LoRA 指令微调 + CoT 关键代码抽取。
- **数据集**：需核对原文。
- **评价指标**：需核对原文。
- **主要结论**：可输出含成因、位置、修复建议的解释，并检测漏洞类型。
- **明显局限**：解释真实性、定位精度、修复建议可编译性需核对原文；无 API 授权逻辑证据。

### [10] Multitask-Based Evaluation of Open-Source LLM on Software Vulnerability
- **要解决的问题**：定量评估开源 LLM 在不同漏洞任务中的真实能力。
- **核心方法**：在 Big-Vul 上构建多任务评测流水线（检测、评估、定位、描述）。
- **数据集**：Big-Vul。
- **评价指标**：材料未完整列出，需核对原文。
- **主要结论**：**现有 SOTA 方法与预训练 LM 在漏洞检测上通常优于 LLM**；部分 LLM 在评估与定位上较强；冗长输出损害性能。
- **明显局限**：任务为通用软件漏洞，不足以说明 API 业务逻辑与 BOLA/BFLA 场景的能力。

### [11] Defendroid
- **要解决的问题**：Android 代码漏洞的实时检测、类别识别与可解释协同训练。
- **核心方法**：区块链联邦神经网络 + XAI。
- **数据集**：LVDAndro。
- **评价指标**：准确率、F1。
- **主要结论**：基座模型二分类准确率 96% / F1 0.96；多分类准确率 93% / F1 0.91；扩展后均为 96% / 0.96。
- **明显局限**：面向 Android，技术栈与 Web/API 不同；区块链/联邦机制的必要性与部署收益需核对原文。

### [12] Enhancing vulnerability detection efficiency: light-weight LLMs with hybrid code features
- **要解决的问题**：漏洞检测在准确性、结构特征利用与轻量部署之间的平衡。
- **核心方法**：VulACLLM 融合 AST/CFG 特征；比较知识蒸馏（KD）与 LoRA，提出「性能损失/效率收益」量化指标。
- **数据集**：需核对原文。
- **评价指标**：召回率、F1、训练时间、磁盘占用。
- **主要结论**：基础模型召回率 0.73 / F1 0.725；LoRA 压缩后最高召回 **0.82**；一个 epoch 仅 20 分钟，磁盘占用 4.89 MB，可在消费级 GPU 部署。
- **明显局限**：未给出完整精确率；对 API 级输入、跨端点上下文与业务逻辑漏洞无直接证据。

### [13] HyVulDect
- **要解决的问题**：混合语义下的软件漏洞挖掘。
- **核心方法**：基于 GNN 的混合语义漏洞挖掘系统；具体图构建与模型结构需核对原文。
- **数据集 / 评价指标 / 主要结论**：**无公开摘要，全部需核对原文**。
- **明显局限**：依据当前材料无法判断其漏洞类型覆盖、实验质量、开源情况与 API 安全关联。

### [14] Python source code vulnerability detection with named entity recognition
- **要解决的问题**：Python 源码的漏洞检测与类型分类。
- **核心方法**：CodeBERT / RoBERTa / DistilBERT 微调做 token 分类，以 NER 形式检测漏洞。
- **数据集**：覆盖 6 种 CWE；具体规模需核对原文。
- **评价指标**：需核对原文。
- **主要结论**：优于此前 Python 漏洞检测方法。
- **明显局限**：token 级 NER 难以表达跨函数、跨请求与授权状态依赖。
- **开源**：github.com/sonhai1401/PyVulDet-NER

### [15] AIBugHunter
- **要解决的问题**：C/C++ 漏洞定位、分类、严重性评估与修复建议的实用化。
- **核心方法**：VS Code 集成；LineVul + VulRepair 做定位/修复；多目标优化（MOO）分类；Transformer 严重性估计。
- **数据集**：18.8 万+ C/C++ 函数。
- **评价指标**：材料未给出，需核对原文。
- **主要结论**：形成覆盖预测/分类/定位/严重性/修复的工具链。
- **明显局限**：C/C++ 函数级任务与 REST API 授权漏洞差异大；IDE 实时性与修复正确性需核对原文。

## 4. 演进脉络

**2022** — [13] 代表 GNN + 图语义建模阶段，重点仍是函数级源码表示。

**2023** — [15] 把检测延伸到定位/分类/严重性/修复，漏洞挖掘从「是否有漏洞」走向工程工具链。

**2024** — 两条线并行：
- API fuzzing 侧：[4] 解决 schema 与数据库约束不完整导致的测试生成困难。
- LLM 检测侧：[6] 代码图 + LLM；[7] 融合深度模型与 prompting；[8] 长上下文覆盖大项目；[10] **反向泼冷水**指出 LLM 在检测任务上并不稳定优于传统模型；[11][12] 强调可解释性与轻量部署；[14] 以 NER 探索 token 级定位。

**2025** — API 安全从「生成请求」走向「分析授权逻辑」与「解决真实运行依赖」：[2] 形式化建模检测 BOLA；[5] 解决外部服务依赖；[9] LLM 输出扩展到成因/位置/修复。

**2026** — 直指安全语义：[1] 从 resource ID 数据流与授权边界做 BOLA 防御；[3] 明确把访问策略违规、SQLi、XSS 作为 fuzzing oracle，而非只看崩溃。

**已显著推进的问题**：API 请求有效性、外部服务依赖、源码结构建模、LLM 输出解释、漏洞测试用例生成。

**反复出现说明仍未解决的问题**：
1. **API 业务授权语义难以仅靠 OpenAPI、源码或日志完整恢复**（[1][2][3] 从不同角度侧面印证）。
2. **越权漏洞需要身份、对象归属、端点序列与状态迁移，远超函数级 CWE 检测范式**（[6]–[15] 未提供直接解决证据）。
3. LLM 检测可靠性、误报控制、输出冗长、跨项目泛化仍是问题（[7][8][10][12]）。
4. **缺少统一、公开、可复现的实验基准**，能同时评价 API 授权漏洞检测、攻击可执行性与定位解释能力。

## 5. Gap 清单

### Gap 1：面向 BOLA/BFLA 的公开、可执行、带授权语义标注的基准数据集
- **(a) 缺口**：现有材料中没有同时包含 API 规范、源码或部署环境、用户角色、对象归属、请求序列、BOLA/BFLA 真值标签与可复现攻击测试的公开基准。
- **(b) 证据**：[1] 用 10 个 GitHub 项目 + CVE；[2] 用 OpenAPI + 日志；[3] 用人工样例 + 脆弱 API + WFD API。三者数据形态分散。
- **(c) 强度**：中
- **(d) 三区适配**：能，但「只做数据集」通常不够。需配套提出授权语义建模或检测/验证方法，并以可复现实验与强基线验证。
- **(e) 坑**：BOLA/BFLA 标签需严格定义；不能只把 URL 里的 ID 改掉就标为漏洞；必须区分未认证 / 未授权 / 资源不存在 / 业务规则拒绝 / 真实越权。

### Gap 2：LLM 驱动的 API 授权语义推断与 BOLA/BFLA 检测 ★
- **(a) 缺口**：LLM 研究集中于函数级源码 CWE；BOLA 研究集中于静态 ID 流、OpenAPI/Petri 网或 fuzzing。尚未见 LLM 将 OpenAPI、路由、控制器、认证中间件、数据访问代码与测试响应**联合推断**授权规则。
- **(b) 证据**：[1][2] 是非 LLM 的 BOLA 分析；[6]–[10][12][14] 是通用源码 LLM 检测或评测；[3] 是非 LLM API 安全 oracle。
- **(c) 强度**：**强**
- **(d) 三区适配**：能，且是最直接的「新方法 + 公开数据集实验」切口。关键不是宣称 LLM 能识别越权，而是让 LLM 产出**结构化授权假设**，并由静态/动态证据验证。
- **(e) 坑**：LLM 幻觉授权规则、训练数据泄漏、提示词敏感性、成本与不可复现。**必须使用确定性 verifier，不能以 LLM 自评作为唯一 oracle。**

### Gap 3：面向 API 越权的「推断—攻击生成—运行时验证」闭环
- **(a) 缺口**：[1] 偏静态授权边界，[2] 偏模型与日志，[3] 偏 fuzzing oracle；没有从授权策略推断、测试序列生成到真实运行时漏洞证据与最小化 PoC 的统一闭环。
- **(b) 证据**：[1][2][3][4][5]
- **(c) 强度**：中
- **(d) 三区适配**：能。尤其适合 JISA——输出可复现 PoC、受影响端点、角色与对象关系，安全实用性突出。
- **(e) 坑**：必须证明不是只发现「权限不足导致 403」或因测试环境重置失败产生的假阳性；需控制测试账户、对象所有权与状态污染。

### Gap 4：BFLA 与复杂角色/工作流授权的系统评测
- **(a) 缺口**：材料中明确聚焦 BOLA 的只有 [1][2]，[3] 泛称访问策略违规；没有 BFLA、角色层级、租户隔离、审批状态、跨端点工作流授权的专门方法与标准化评价。
- **(b) 证据**：[1][2][3]
- **(c) 强度**：中
- **(d) 三区适配**：能。前提是把 BFLA 明确定义为「低权限角色调用高权限功能」的授权失效，并提供真实可执行场景，而非只做 endpoint role 标签分类。
- **(e) 坑**：角色权限配置不完整时很难判定「设计如此」还是「漏洞」；应以应用预期策略、测试夹具或人工审计形成真值。

### Gap 5：把 API 调用图、数据流与身份/对象状态联合表示
- **(a) 缺口**：通用 LLM/图模型利用 AST、CFG、代码图（[6][12][13]）；BOLA 工作关注 resource ID 流（[1]）。但未见统一图表示同时建模端点调用、认证身份、资源对象、数据库归属关系与响应状态。
- **(b) 证据**：[1][6][12][13]
- **(c) 强度**：中
- **(d) 三区适配**：能。可提出 Authorization Interaction Graph 之类结构化表示，再用轻量 GNN/LLM 做候选筛选，动态测试验证。
- **(e) 坑**：图构建成本高、跨语言框架泛化弱、静态依赖解析不完整。需量化构图开销并做去除不同边类型的消融。

### Gap 6：LLM 解释在 API 越权场景的可验证性
- **(a) 缺口**：[9] 可输出成因/位置/修复建议，但未用于 API 授权漏洞，也无「解释是否与可执行攻击和授权证据一致」的评价。
- **(b) 证据**：[1][2][3][9][10]
- **(c) 强度**：中
- **(d) 三区适配**：可以，但单纯「生成解释」创新性偏弱。更合适的主张是：解释必须包含攻击角色、受害对象、端点序列、授权缺失位置与可验证 PoC。
- **(e) 坑**：自然语言解释很容易「看起来合理」。应评估证据一致率、定位准确率与人工安全专家可用性，而非只展示案例。

### Gap 7：API 安全 oracle 的误报、覆盖率与泛化评测
- **(a) 缺口**：[3] 表明安全 oracle 是必要方向，但未提供其在 BOLA/BFLA 上的细粒度误报率、不同身份策略下的泛化、最小攻击序列质量等信息。
- **(b) 证据**：[3][4][5]
- **(c) 强度**：弱到中
- **(d) 三区适配**：仅优化某个 oracle 未必足够；若结合授权策略推断、可复现基准与跨应用实验，则可形成可投稿工作。
- **(e) 坑**：不能把覆盖率提升等同于越权检测提升；需报告 precision、recall、PoC 成功率、执行成本与时间预算。

### ★ API 越权 × LLM 辅助检测的交叉空白（专项回答）

最明确的交叉空白是：**尚未见到把 LLM 用于跨 OpenAPI、路由代码、认证/鉴权逻辑、数据库对象归属与多角色交互轨迹的授权策略推断，并通过 fuzzing 或执行测试证明 BOLA/BFLA 的方法。**

具体而言：
- [1] 能跟踪 resource ID 与授权边界，但未显示用 LLM 处理复杂、隐式或分散的业务授权逻辑。
- [2] 能从 OpenAPI 与日志进入形式化检测，但对规格中未表达的真实权限规则可能受限；未显示 LLM 补全或解释这些规则。
- [3] 有安全 oracle 与可执行测试生成，但未显示 LLM 生成角色敏感测试序列、归纳对象归属或降低误报。
- [6]–[10][12][14] 说明 LLM、代码结构、解释与轻量化可用于通用漏洞任务，但无证据覆盖 API 授权逻辑漏洞。
- [10] 尤其提示：**LLM 不能作为「天然更强的检测器」来写 claim**，应定位为候选授权规则/攻击路径生成器，并用静态或动态验证器兜底。

## 6. 面向 JISA 的投稿方向建议

### 方向一：LLM 辅助授权语义推断与可验证 BOLA/BFLA 挖掘
- **核心 claim**：提出结合 LLM、resource ID 数据流与动态验证的框架，从 API 规范与实现中推断候选授权约束，生成多角色攻击测试，并以可执行 PoC 验证 BOLA/BFLA。
- **目标数据集**：自建并公开的 REST API 授权漏洞基准（OpenAPI + 代码/容器环境 + 角色 + 对象归属 + 攻击序列 + 漏洞类型 + 修复版本）；可补充 [3] 提到的 WFD API，适用性需核对原文。
- **baseline**：[1] 的 ID 数据流/授权边界；[2] 的 OpenAPI→Petri 网；[3] 的 EvoMaster 安全 oracle；外加「不使用 LLM」的规则/静态分析消融。
- **卖点**：把 LLM 放在「复杂语义推断」位置，最终判断交给可执行验证；输出 PoC 与可解释授权证据。
- **最可能被攻击的角度**：数据集规模偏小、标签主观、LLM 幻觉、基线复现不公平、案例驱动而非总体统计。应预先设计双人标注/仲裁、漏洞真值证据与多次重复实验。

### 方向二：面向 BOLA/BFLA 的状态感知安全 Fuzzing Oracle
- **核心 claim**：提出状态感知、对象归属感知的 REST API fuzzing oracle，自动构造「攻击者—受害者—资源—端点序列」，发现传统状态码/崩溃 oracle 遗漏的授权失效。
- **目标数据集**：参考 [3] 的 52 个 API 评测设置（可复用范围需核对原文）；另构建并公开带角色、资源所有权与多步骤业务流的基准。
- **baseline**：[3] 的安全 fuzzing oracle；[4] 的白盒 REST API fuzzing；[1] 的静态 resource ID 分析；朴素随机身份/ID 变异策略。
- **卖点**：不依赖 LLM 也能形成扎实的安全测试论文；目标清晰、可复现、PoC 有说服力。
- **最可能被攻击的角度**：被质疑只是「更复杂的 ID 替换」。必须证明状态与对象归属建模带来显著增益，并展示 BFLA、跨端点、多租户等非平凡案例。

### 方向三：API 授权交互图 + 轻量模型的跨项目越权候选筛选
- **核心 claim**：构建由端点、角色、resource ID、数据访问、认证检查与调用边组成的授权交互图，用轻量图模型或轻量 LLM 对潜在越权路径排序，再由动态执行确认。
- **目标数据集**：公开构建的多语言/多框架 REST API 授权漏洞数据集；若只覆盖单一框架，须明确边界，不可泛化声称「适用于所有 API」。
- **baseline**：[1] 静态 ID 数据流；[2] 形式化 OpenAPI 分析；[6] 图增强 LLM 的结构信息思想；[12] AST/CFG 混合特征与轻量化思想。对照应含：仅代码图 / 仅 OpenAPI / 仅 ID 数据流 / 完整交互图。
- **卖点**：避免把 LLM 当黑箱决策器；可解释输出「哪个角色可沿哪个端点访问哪个不属于它的对象」，并兼顾效率。
- **最可能被攻击的角度**：图构建规则是否人为编码了答案；跨框架解析是否可靠；相比 [1] 是否只是特征堆叠。需消融、运行开销统计与未见项目测试。
