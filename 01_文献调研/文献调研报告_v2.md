# Web/API 授权安全与漏洞挖掘：更新版文献调研

## 证据范围与阅读规则

本报告仅使用本目录材料：39 篇元数据/摘要、12 篇 PDF 全文精读摘录、BibTeX 与 v1 文档。`【全文】`表示结论可回溯到 `um_fulltext.md` 的页码锚点；`【摘要】`表示未读原论文全文，不把摘要的省略信息补写为事实。编号 [1]–[39] 保持 `_digest_inline.txt`，cite_key 为 `-` 的项目仅有编号可用。所有“未提供”的信息均显式标注为待核对。

## 1. 领域地图

### A. BOLA/BFLA 检测与工具

该簇要回答“某次跨身份访问是否真的违反对象或功能授权”。静态路线从数据库所有权、resource-ID 传播、权限检查与认证路径中找缺失检查（[1]、[16] Hua24、[19] Liu25e、[20] Shi25、[21] Fen25）；动态/黑盒路线使用账户交换、参数变异、反馈或 SQL 证据（[17] Dha25、[18] Liu25b、[22] Sch25、[26] Sun25b、[38] Che25c）。二者关系是互补：静态路径可说明“何处可能缺检查”，动态路径可证明“跨账户操作是否成功”。共同瓶颈是授权 oracle，而不只是生成请求。

### B. 静态权限推断与策略提取

该簇将分散在代码、数据库查询、框架检查或日志中的实现恢复为 RBAC、对象归属或数据访问策略。[34] Le21 从日志和组合测试恢复 RBAC，但需人工标签规则；[35] Ber20 从 Java 授权事实建图；[36] Zha24b 用 concolic execution 将 Rails 的路径条件/SQL 合成为策略；[16] Hua24 推断四种对象模型。它们说明“策略抽取”并非空白，真正尚难的是跨制品、端点级、可用于运行时对象归属测试的可验证抽取。

### C. Oracle、变形与差分测试理论

[23] Cha22、[24] Mai19 将未知绝对预期转化为多次执行间必须成立的关系；[38] Che25c 的双账户 ID 交换给出伦理化黑盒范式；[18] Liu25b 用操作反馈而非响应相似度判断读/写成功；[17] Dha25 以后台 SQL 作为灰盒证据。该簇直接约束任何“状态码=漏洞”的粗糙设计：403、404、200 空体和 200 错误页并不能单独裁决越权。

### D. API 状态探索、fuzzing 与执行环境

[25] Atl19 的 producer-consumer 推断和动态反馈奠定状态序列探索；[3] 将安全 oracle 接入 EvoMaster；[4] 用白盒启发式处理不完整 schema/SQL 约束；[5] 以自动 mock 处理外部服务依赖。这一簇解决“如何到达可测试状态”，但通常不充分解决“哪一种跨身份响应是越权”。

### E. LLM 辅助安全推理

LLM 在该领域已有多个受限角色：UPR 变量评分 [27] Wan24b、候选规格生成再由 verifier 审核 [28] Wen24、参数选择 [17] Dha25、IoT 代码信息抽取 [30] Wan25d、微服务程序分析规划/语义判断 [37] Li26g，以及直接授权测试合成 [29] Udd26。关系是：LLM 可提高候选覆盖或语义理解，但不能被当作漏洞真值 oracle。

### F. LLM 能力边界

[10] 发现通用漏洞检测中传统 SOTA/预训练模型通常优于 LLM；[31] 发现隐含、缺失约束与多步状态依赖是稳定失败区；[32] FormalBench 显示模型对循环、语义等价变换和完整形式规格不稳。因此，将 LLM 限定为受控候选器、让可重放证据裁决，既是工程策略也是实验必须验证的假设。

### G. 数据集、真值与经典基础

[33] Cro23 显示真实漏洞数据集中 20–71% 标签可能不准确、17–99% 数据点可能重复；[39] AUTHSCOPE 是早期自动发现脆弱授权代表；[13]–[15] 是函数/Token 级通用漏洞检测或工具，适合作为“不能替代 API 授权评测”的反例，而非主基线。

## 2. 逐篇速览

### [1] BolaZ【摘要】
- 要解决的问题：REST API 的 BOLA 与 resource-ID 篡改。
- 核心方法：静态污点跟踪，将 API 划为 ID producer/consumer，推断授权区间并适配最佳实践逻辑。
- 数据集：10 个 GitHub 项目及 CVE 收集缺陷。
- 评价指标：摘要未完整给出。
- 主要结论：发现 35 个野生 BOLA。
- 明显局限：纯静态；运行时误报、SELECT/复杂状态与开源状态需核对。

### [2] OpenAPI→彩色 Petri 网【摘要】
- 要解决的问题：从 REST OpenAPI 与日志检测 BOLA 攻击。
- 核心方法：OpenAPI 转 colored Petri net，分析 Web-server 执行痕迹。
- 数据集：一个脆弱 Web 应用案例；日志。
- 评价指标：所述场景准确率 >95%。
- 主要结论：规格+日志可用于 BOLA 风险检测。
- 明显局限：OpenAPI 未必表达真实授权；案例规模和真值构造待核对。

### [3] EvoMaster access-policy oracle【摘要】
- 要解决的问题：REST fuzzer 仅看崩溃而漏掉访问策略违规、SQLi、XSS。
- 核心方法：在 fuzzing 后执行安全测试阶段，输出多语言可执行测试。
- 数据集：9 人工、8 vulnerable-by-design、36 WFD，共 52 API。
- 评价指标：摘要未给完整 precision/recall。
- 主要结论：安全 oracle 集成可发现多类问题。
- 明显局限：角色/策略输入、WFD 获取和 BOLA/BFLA 细节须核对全文。

### [4] 白盒 REST fuzzing 启发式【摘要】
- 要解决的问题：API/SQL schema 不完整导致状态化 fuzzing 无法生成有效请求。
- 核心方法：EvoMaster 白盒搜索启发式。
- 数据集：14 个 EMB API 与 1 个工业 API。
- 评价指标：覆盖率、fault finding（具体值未给）。
- 主要结论：部分 API 有明显改进。
- 明显局限：不以授权 oracle 为目标。

### [5] 搜索式 mock generation【摘要】
- 要解决的问题：外部 Web 服务依赖阻碍 REST fuzzing。
- 核心方法：插桩发现交互/解析，搜索 mock 响应，DNS 导流。
- 数据集：4 个 EMB 开源 REST API、1 个工业 API。
- 评价指标：行覆盖和 fault finding。
- 主要结论：自动 mock 可改善含依赖系统的可测性。
- 明显局限：未提供授权语义/越权真值。

### [6] GRACE【摘要】
- 要解决的问题：纯文本 LLM 漏洞检测忽略代码结构。
- 核心方法：代码图结构 + 检索 in-context demonstrations。
- 数据集：Devign、Reveal、Big-Vul。
- 评价指标：F1。
- 主要结论：相对 6 个 SOTA 至少提升 28.65% F1。
- 明显局限：函数/通用漏洞数据并不能证明 API 业务授权能力。

### [7] DLAP【摘要】
- 要解决的问题：DL 泛化/解释不足且原始 prompt 检测性能低。
- 核心方法：深度模型与 LLM prompting 融合。
- 数据集：摘要未列。
- 评价指标：多指标但未列数值。
- 主要结论：优于多种 prompting 与 fine-tuning 对照。
- 明显局限：未提供 API 授权任务证据。

### [8] SecureQwen【摘要】
- 要解决的问题：大规模 Python 代码库的多 CWE 检测。
- 核心方法：64K context decoder-only Transformer。
- 数据集：187.5 万函数片段，来自 GitHub、Codeparrot 与 GPT-4o 合成数据。
- 评价指标：F1。
- 主要结论：14 类 CWE F1 为 84%–99%。
- 明显局限：函数级、合成数据与泄漏风险；不能外推至跨请求授权。

### [9] LLMVulExp【摘要】

- 评价指标：检测与解释指标，具体待核对。
- 主要结论：可联合检测类型并生成解释。
- 明显局限：解释真实性与 API 授权适用性未证实。

### [10] 开源 LLM 漏洞多任务评测【摘要】
- 要解决的问题：量化 LLM 在检测、评估、定位、描述上的真实能力。

- 数据集：Big-Vul。
- 评价指标：四任务指标（具体待核对）。
- 主要结论：传统 SOTA/预训练 LM 通常优于 LLM 检测；LLM 在评估/定位/描述有局部优势。

### [11] Defendroid【摘要】

### [16] BolaRay / Hua24【全文】
- 要解决的问题：数据库驱动应用中的 BOLA。
- 核心方法：SQL+静态分析，推断 ownership、membership、hierarchical、status 四类模型，并查敏感操作是否有相应检查。
- 数据集：25 个开源 PHP 应用；101 个手工标注 BOLA 用于经验研究。
- 评价指标：人工审查报告、维护者确认、FPR。
- 主要结论：247 报告中 193 true，FPR 21.86%；155 已确认、52 CVE。
- 明显局限：需手工 DAL specification；仅 PHP；忽略 SELECT；不查错误检查；启发式非 sound/complete。

### [17] BACFuzz / Dha25【全文】
- 要解决的问题：静默的 BOLA/BFLA 难以被常规 fuzzing oracle 发现。
- 核心方法：LLM 识别 reference parameters，PHP 轻量插桩捕捉 SQL，以 DML/WHERE 匹配和 multiple checking 裁决。
- 数据集：20 个真实 PHP 应用，含 15 CVE、DVWA/XVWA。
- 评价指标：已知问题检出、新漏洞、FP。
- 主要结论：检出 16/17 已知问题、26 新 BAC；表中合计 11 FP。
- 明显局限：RBAC、DML；漏 SELECT 泄露、复杂状态前置；假定已有用户/初始数据。

### [18] BACScan / Liu25b【摘要】

- 数据集：20 个真实应用。
- 评价指标：漏洞/新漏洞/CVE 数。
- 主要结论：89 漏洞、54 未报告、35 CVE。
- 明显局限：摘要未给 FPR、真值与状态搭建细节。

### [19] MOCGuard / Liu25e【摘要】

### [23] MST-wi / Cha22【全文】

### [24] MST / Mai19【全文】

### [25] RESTler / Atl19【摘要】

### [26] LLM-assisted IDOR / Sun25b【摘要】
- 要解决的问题：医院小程序 IDOR 的合规黑盒检测。
- 核心方法：token substitution probing；LLM 做字段识别、请求分类与差分响应分析。

### [27] UPR variables / Wan24b【全文】
- 要解决的问题：大程序中用户权限相关变量筛选。
- 核心方法：PDG 变量子图；LLM 给 statement 0–10 分，算法聚合为 UPR 分。
- 数据集：nginx、sshd、sudo 等 7 个开源程序。
- 评价指标：FPR、人工审查节省、启发式对比。
- 主要结论：FPR 13.49%；4455 变量中仅 645 需审查；优于启发式 FPR 54.53%。
- 明显局限：局部语句丢上下文；开源训练分布/每语句成本；最终仍须人工确认。

### [28] AutoSpec / Wen24【全文】
- 要解决的问题：自动形式规格综合。
- 核心方法：静态扩展 call graph 分解，LLM 填候选 ACSL，Frama-C/WP 查 legality、satisfiability、adequacy。
- 数据集：251 C 程序、四基准加 X509-parser。
- 评价指标：验证成功率、相对基线。
- 主要结论：199/251=79%，相对工具 1.592×。
- 明显局限：缺外部上下文、语义 bug、整项目扩展性和 LLM 误差累积。

### [29] 微服务授权测试 / Udd26【摘要】
- 要解决的问题：跨服务 authorization blindspots/policy drift。
- 核心方法：policy-enriched IR 确定性引导 GPT-5 生成 downstream-aware 测试。
- 数据集：Train-Ticket。
- 评价指标：语义有效测试、drift validation 错误率。
- 主要结论：100% semantically valid tests，97.4% error-free drift validation。
- 明显局限：微服务策略漂移与单体 BOLA 不同；但“IR+LLM+可执行授权测试”已被覆盖。

### [30] ACBreaker / Wan25d【全文】
- 要解决的问题：IoT 受保护 Web 接口绕过。
- 核心方法：代码切片+LLM 两轮 JSON 信息抽取，mutation fuzzer，三层差分过滤。
- 数据集：11 个商用 IoT 设备，1,274,646 LOC。
- 评价指标：漏洞、接口数、baseline 对比、抽取能力。
- 主要结论：39 漏洞、508 接口；nomore403=4、Boofuzz=0；GPT-4o 识别 124 有效接口。
- 明显局限：HTTP-only；配置文件/异构协议限制；相似度阈值与对象归属不是同一问题。

### [31] 隐含安全不变量边界 / Wan26【摘要】
- 要解决的问题：LLM 对缺失 guard、多步工作流等隐含不变量的能力边界。
- 核心方法：六层语义分类、真实 commit 片段与受控样本、两种 prompt/context。
- 数据集：混合真实/受控评测套件（规模未列）。
- 评价指标：识别、定位、不变量重构分层质量。
- 主要结论：更多上下文有局部改善；缺失约束/多步状态出现稳定失败及不一致叙事。
- 明显局限：评测研究，不提供 API oracle。

### [32] FormalBench / Lec25【全文】
- 要解决的问题：LLM 形式规格/程序语义推理。
- 核心方法：700 Java 基础程序与 6219 语义等价变体，JML 规格验证。
- 数据集：FormalBench-Base、FormalBench-Diverse。
- 评价指标：success、failure、completeness、flip rate。
- 主要结论：GPT-4o zero-shot success 11.2%；语义等价 flip 27.2%–39.2%；self-repair 提升成功约 25%。
- 明显局限：Java/JML、unknown verifier 结果、mutation proxy；强烈反对让 LLM 独立裁决。

### [33] 数据质量 / Cro23【全文】
- 要解决的问题：软件漏洞数据集的标签和重复问题。
- 核心方法：审计 accuracy、uniqueness、consistency、completeness、currentness。
- 数据集：Big-Vul、Devign、D2A、Juliet。
- 评价指标：五维质量值及人工标签抽查。
- 主要结论：真实集 vulnerable 标签误差 D2A 71.4%、Big-Vul 45.7%、Devign 20%；重复 17–99%。
- 明显局限：结论针对所审四集；不自动保证新基准质量。

### [34] ReACP / Le21【全文】
- 要解决的问题：缺失/硬编码 Web RBAC 策略的逆向恢复。
- 核心方法：日志/HTTP 特征、组合测试、C4.5 决策树与 meta-attributes。
- 数据集：iTrust、TaskFreak、WordPress、SECP。
- 评价指标：相对实施 Gold Standard 的策略正确率、AC issue 数。
- 主要结论：应用特定规则平均正确 97.8%，发现 64 个 AC issues。
- 明显局限：半自动、依赖人工标签/输入；RBAC-only；观察不到复杂业务逻辑和不可达状态。

### [35] SeeAuthz / Ber20【摘要】
- 要解决的问题：从已实施授权提取图并与计划策略比较。
- 核心方法：Java 上下文敏感授权事实分析、authorization graph。
- 数据集：开源内容仓库与闭源制造系统。
- 评价指标：摘要未列。
- 主要结论：可配置到 Shiro 并讨论迁移。
- 明显局限：计划策略与框架配置依赖；未给 API 动态证据。

### [36] Ote / Zha24b【全文】
- 要解决的问题：从 Web 应用隐式访问检查/查询过滤提取数据库策略。
- 核心方法：Rails concolic execution 记录路径/SQL，LLM relevance judge 剪枝，合成 SQL view 并用 Blockaid 辅助。
- 数据集：diaspora、Autolab、The Odin Project。
- 评价指标：相对手写策略的错误和 tightness。
- 主要结论：发现手写策略过宽及 Autolab 外部库禁用检查的 bug。
- 明显局限：无 negation/复杂查询表达；bounded execution 和 LLM judge 不保证 complete/tight；需人工约束。

### [37] NeO / Li26g【全文】
- 要解决的问题：polyglot microservices 的权限提升。
- 核心方法：LLM agent 规划+CodeQL 搜索原语+跨服务流拼接+Z3 可满足性验证。
- 数据集：25 开源微服务、7 语言、6.2 MLOC；4 应用/20 known-vuln 真值集。
- 评价指标：precision、recall、0-day、时间、成本。
- 主要结论：P=81.0%、R=85.0%，24 zero-day；均值 1.6 h、$18/应用。
- 明显局限：CodeQL 动态特性、配置/部署、框架 URL 语义及模型/prompt 敏感。

### [38] VSF / Che25c【摘要】
- 要解决的问题：不泄露未知用户数据前提下的大规模野外 BAC 检测。
- 核心方法：两账户、交换 identifier 的伦理黑盒框架。
- 数据集：成功测试的 100 个 Web 应用。
- 评价指标：AC-sensitive endpoint、可利用 flaw。
- 主要结论：584 潜在端点，19 个可利用漏洞，分属 7 站点并负责披露。
- 明显局限：双账户交换不足以恢复复杂角色/状态；没有源码辅助。

### [39] AUTHSCOPE / Zuo17【摘要】
- 要解决的问题：在线服务中的脆弱授权自动发现。
- 核心方法：本材料无摘要、全文不可得。
- 数据集：未提供。
- 评价指标：未提供。
- 主要结论：仅可确认其为早期经典授权发现工作。
- 明显局限：任何机制/数字均须核对原文，不应填补。

## 4. 演进脉络（2011–2026）

- **2011–2017：策略/授权发现奠基。** RoleCast（材料提及，未给可引编号）和 AUTHSCOPE [Zuo17] 代表早期“从实现或在线服务发现授权问题”；2016 的 CanCheck（材料提及，未提供本次条目）与 2017 AUTHSCOPE 表明授权验证早于 LLM。
- **2019–2021：状态序列与策略逆向。** RESTler [Atl19] 将 producer-consumer 依赖用于状态 API；Mai19/Cha22 将 oracle problem 写成多执行关系；ReACP [Le21] 从日志恢复 RBAC，但依赖观测与人工规则。
- **2022–2024：从授权图到数据库/规格证据。** SeeAuthz [Ber20]、BolaRay [Hua24]、Ote [Zha24b] 分别从授权事实、SQL/静态和 concolic query traces 提取策略；OpenAPI→Petri 网 [2] 说明规格/日志路线。真正解决的是“可从实现中抽取部分授权事实”，未解决的是意图、完整性和跨制品覆盖。
- **2025：BAC 动态验证成熟。** MOCGuard、PCFinder、BACScan、BACFuzz、A2CT、VSF 分别强化数据库所有权、permission check、操作反馈、SQL oracle、通用 Web 测试和伦理黑盒；说明 BOLA 不是只改 ID，BFLA、写操作和反馈均重要。
- **2024–2026：LLM 被纳入但受约束。** Wan24b、AutoSpec、ACBreaker、NeO、Udd26 已将 LLM 置于受限语义任务、验证器/求解器/运行时证据旁。FormalBench [Lec25] 与 Wan26 同时说明：复杂状态和隐含缺失检查仍是可靠性边界。

**已实质推进：**状态化请求生成、DB/代码中的部分所有权建模、访问控制缺失检查、双账户差分、可执行测试生成。

**反复出现、仍未解决：**(i) 不完整规格与真实授权语义的差距；(ii) SELECT 泄露和复杂状态/工作流；(iii) 对象归属、拒绝语义和异步噪声下的可靠 oracle；(iv) 统一公开、可审计、同时包含正负授权样本的真值基准；(v) LLM 输出的证据归因、稳定性和成本。

## 5. 可发表 gap 清单

### Gap 1：可审计的对象归属真值基准
- 缺口：现有 API/BAC 评测的应用、漏洞、标签和状态脚本分散，少有“创建记录—对象归属—触发请求—修复 diff”闭环。
- 证据：[3] 的 52 API、[16] Hua24 的人工标注、[17] Dha25 的 CVE/真实应用、[33] Cro23 的标签错误。
- 强度：强。
- 三区创新性：**能**，但必须与可复用 oracle/工具绑定；单做数据集不足。
- 坑：注入型真值的现实性、版本泄漏、把未报告当阴性；须分离注入、修复版与真实 CVE。

### Gap 2：校准的多账户对象级 oracle
- 缺口：响应相似度、状态码、SQL DML 和操作反馈各有盲点；没有从本材料看到一个公开、统一评测的“自有对象—受害者对象—幽灵对象—稳定性”校准协议。
- 证据：[17] Dha25 漏 SELECT/复杂状态；[18] Liu25b 改进响应相似度；[23][24] 变形关系；[30] Wan25d 三层差分。
- 强度：中强。
- 三区创新性：**能**，前提是直接证明比朴素 ID 替换与现有 oracle 更低 FPR。
- 坑：不是差分测试首创；必须把贡献写成授权对象归属的校准与实测效益。

### Gap 3：复杂状态下的 BOLA/BFLA 可达性
- 缺口：多数 BAC 工具假定初始数据或难处理 precondition；状态探索工具又不懂授权语义。
- 证据：[17] Dha25 明确不处理复杂状态；[25] Atl19 状态生成；[4] 不完整 schema；[31] LLM 对多步不变量失败。
- 强度：强。
- 三区创新性：**能**，以确定性 producer-consumer 状态搭建+归属构造为新方法。
- 坑：不要把 LLM plan 当 ground truth；不可达路径必须报告而非静默跳过。

### Gap 4：SELECT 型 BOLA/隐私泄露的动态可证伪
- 缺口：BolaRay 为降 FP 忽略 SELECT，BACFuzz 依赖 DML；读泄露仍需要对象归属证据。
- 证据：[16] Hua24、[17] Dha25、[18] Liu25b。
- 强度：中强。
- 三区创新性：**能**，若能定义稳定的受害者字段/归属验证并在真实应用复现。
- 坑：敏感字段、分页和缓存可能让 read oracle 错判；需最小化泄露和伦理边界。

### Gap 5：BFLA 与对象级关系的统一、可解释报告
- 缺口：BFLA 与 BOLA 同被称 BAC，但 test setup、真值与结果粒度常混杂。
- 证据：[17] Dha25、[22] Sch25、[3]。
- 强度：中。
- 三区创新性：**可行但风险高**；统一 IR 要展示 relation/action 分别带来的增益。
- 坑：角色目录不全时，低权限失败不是 BFLA；应先做 BOLA 主任务。

### Gap 6：LLM clause 的证据归因与失效审计
- 缺口：已有 LLM+授权工作多报告端到端结果，少见逐 clause 的 source span 有效性、受控词表一致性和跨运行稳定性评测。
- 证据：[27] Wan24b 的局部评分失败、[28] Wen24 的 validator、[32] Lec25、[37] Li26g、[29] Udd26。
- 强度：中。
- 三区创新性：**能**，更适合作为 Gap 2/3 的可靠性子贡献。
- 坑：source citation 不证明语义正确；不能把“有出处”写成“真意图”。

### Gap 7：可复现实验中的拒绝语义与异步噪声处理
- 缺口：拒绝可能是 403/404/200 错误体，异步状态、限流、缓存会污染差分结论。
- 证据：[23] Cha22 的异步 FP、[24] Mai19 的页面噪声、[30] Wan25d 的过滤、[38] Che25c 的黑盒边界。
- 强度：中。
- 三区创新性：**能**，若报告 inconclusive 率、重复执行与按应用校准。
- 坑：预先选择阈值/签名会过拟合靶场；规则和测试预算要在盲测前冻结。

### Gap 8：授权安全基准的数据质量协议
- 缺口：CVE/commit/人工标签都不天然可信，且不应将未发现漏洞当安全阴性。
- 证据：[33] Cro23；[16] Hua24 的多作者标注+维护者确认；[17] Dha25 的披露流程。
- 强度：强。
- 三区创新性：**可作为配套贡献**，单独较弱。
- 坑：构造式真值不等于真实分布；公开时须做版本、重复、泄露和伦理审计。

### LLM 授权语义推断 × API 越权检测：交叉空白到底在哪里？

交叉点**不是空白大陆**。最接近的工作为：BACFuzz [Dha25]（LLM 参数选择+SQL oracle）、Sun25b（LLM IDOR 请求/字段分析+差分）、ACBreaker [Wan25d]（LLM 代码抽取+fuzzer+差分）、JAuthGuard [Fen25]（LLM prompt 辅助静态 control defect）、Udd26（policy IR+GPT-5 授权测试）、NeO [Li26g]（LLM+程序分析/SMT 权限提升）。

真正可辩护的窄空白是：**在可控 API 部署中，用跨制品、span-grounded 的候选 clause 来驱动构造式“攻击者—受害者—同构/幽灵对象”测试，并以对象归属可回读、重复稳定的动态证据裁决 BOLA；同时把 clause 正确性与端到端性能分开评测。** 它距离上述工作的差别分别是：Dha25 缺 SELECT/复杂状态且 LLM 不归纳 clause；Sun25b 为野外小程序 token probing；Wan25d 没有多账户对象归属；Udd26 是微服务 drift；NeO 的终局判断仍含 LLM。这个差异只有在共享/可审计真值上的实验才能成立。

## 6. 对 v1 报告的修正

1. **“尚未见 LLM+API 授权语义+可验证检测”错误，须撤回。** [17] Dha25、[26] Sun25b、[29] Udd26、[30] Wan25d、[37] Li26g、[21] Fen25 已直接或部分覆盖该交叉。v1 使用仅 15 篇摘要而遗漏了 Undermind 条目。
2. **“AuthOracle 与 BolaZ 的差异清晰”需弱化。** BolaRay [Hua24] 已自动推断四类对象授权模型，BolaZ [1] 又有 authorization-guided 静态边界；不能把现有静态工作概括为“不做语义”。可区分的是运行时构造式真值与读/写差分裁决。
3. **“[3] 需要人工告知角色与策略”没有本次材料证据。** 摘要只说明自动 access-policy violation checks；在全文核实前改为“其角色/策略输入机制待核对”。
4. **“三重对照差分 oracle 是最硬技术点”需去首创暗示。** 变形测试、双账户交换、操作反馈与 ACBreaker 差分过滤均已存在。正确表述是“一个待验证的对象归属校准组合”。
5. **“朴素 oracle FPR 可由 40%+ 降至 <10%”没有证据，必须删除。** 可将其改成预注册假设，且报告置信区间和 paired test。
6. **BolaRay 数字在 v1 不准确/不完整。** 全文为 247 报告、193 true、FPR 21.86%、155 确认、52 CVE；不是“193 漏洞、52 CVE”即可概括。[Hua24]
7. **BACScan 数字在 v1 不准确。** 材料为 89 漏洞、54 未报告、35 CVE，不是“89、35”。[Liu25b]
8. **“LLM 从服务端代码恢复授权语义仍少”可以保留但必须限缩。** Ote、ReACP、BolaRay、NeO、Udd26 已做策略/语义/测试的不同部分；应改为“端点级、跨制品、动态对象归属裁决的统一评测仍未由本材料证明成熟”。
9. **AuthBench 的注入真值不能等同真实 CVE。** Cro23 支持审计式真值，但也要求将注入集、修复版、真实缺陷集分开报告。[Cro23]
10. **GraphQL、crAPI、VAmPI、Juice Shop、PetClinic 和 WFD 的具体漏洞清单/可用性未由材料证明。** 只能作为候选，不可写成已知可直接评测数据集。

## 7. 面向 JISA 的收敛建议

最稳妥的论文命题是“**Evidence-grounded, state-calibrated oracle for BOLA detection**”，而不是“LLM 自动恢复授权意图”。方法主线应是：确定性抽取证据图 → 受控 LLM/规则产生候选 clause → 类型/跨度门控 → RESTler 式状态搭建 → 自有/受害/幽灵对象多账户动态判定 → 可回读 PoC。实验主张只围绕：precision、recall、FPR、inconclusive rate、状态可达率、重放率、成本与消融。若 clause 环节不能优于规则/静态基线，则可将其降为可选排序器，论文仍可凭 oracle+benchmark 成立。
