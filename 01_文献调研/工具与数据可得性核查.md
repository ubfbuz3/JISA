## 1. 拿得到的：证据与获取方式

### A1 EvoMaster — 主 baseline，**这是本次核查最重要的收获**

- 实测：`git ls-remote` 对 `github.com/WebFuzzing/EvoMaster` 返回 OK。
- 官方 README 原文（Fault detection 段）：
  > "EvoMaster can generate tests cases that reveal faults/bugs in the tested applications. Different heuristics are employed, like checking for 500 status codes, mismatches from the API schemas, **access policy violations like BOLA**, and SQL Injection. **More than 30 oracles are currently used.**"
- 文档 `docs/faults.md` 实测结果：**共 37 个 fault code**（21 HTTP / 6 Schema / **10 Security**），与「30+ oracles」自洽。
- 获取方式：
  ```bash
  pip install evomaster          # 推荐
  docker pull webfuzzing/evomaster
  # 或从 Release 页下 uber-fat JAR
  ```
- **注意**：uber-fat JAR 需 JDK 17+；而 EMB 的 `jdk_8_maven` 分支需 JDK 8。本机现有 **JDK 1.8.0_291**，够 EMB、可能不够最新 EvoMaster JAR → **需补一个 JDK 17/21**（待办）。

### A2 WFD（=EMB）— 与 Sah26 同语料，可比性问题自动消失

- 实测：`github.com/WebFuzzing/EMB` 可达；`v1.4.0` 有 tag；README 说明更名 WFD。
- 关键点：Sah26（EvoMaster 安全 oracle，JSS 2026）实验用的「**36 个 REST API（WFD）**」就是这份语料。
  → **我们可以用与 SOTA oracle 完全相同的语料**，不用再担心"基线不可比"。
- 结构（对实验直接有用）：
  - `dockerfiles/`：**黑盒**测试用的 Docker Compose，每个 SUT 配 mitmproxy + JaCoCo 收集信息；
  - `experiments/`：`bb-exp.py`（黑盒）、`wb-exp.py`（白盒）、`schedule.py`（并行调度）；
  - REST SUT 举例：Features-Service、Scout-API、ProxyPrint、CatWatch、OCVN、News、Restcountries、Languagetool、CWA-Verification-Server、Disease-sh-API、Cyclotron、SpaceX-API、Realworld-App、**Spring-Pet-Clinic**、Patio-Api、Timbuctoo…
- **诚实标注**：WFD 是**模糊测试基准**，不是 BOLA 基准——**没有 BOLA 真值标注**。
  因此它对我们的用途是 **FPR / 触发率 / 规模**，**不是 recall**。很多 SUT 本身是单用户/无多账户模型，未必能构造跨账户差分。
  → 选入 L4 前必须先筛出**有多账户认证模型**的那几个（如 Spring-Pet-Clinic、Realworld-App、OCVN、CWA-Verification-Server，**逐个核对，不得假设**）。

### A3 crAPI — 官方缺陷清单存在

- 实测可达。官方 `docs/challenges.md` 给出挑战清单，含类别与端点，例如：
  - **Challenge 1**：越权读取他人车辆详情（BOLA）
  - **Challenge 2**：越权读取他人 mechanic report（BOLA，report_id 顺序可枚举）
  - **Challenge 7**：删除他人视频（**BFLA**，需找 admin 端点）
  - Challenge 8–10：Mass Assignment；Challenge 5：内部属性泄露
- 存在第三方整理出的逐项端点答案表（如 `GET /identity/api/v2/vehicle/{vehicleId}/location`、`GET /workshop/api/mechanic/mechanic_report?report_id=N`）——**可作交叉核对线索，不作真值来源**。
- **诚实标注**：这是**教学挑战清单**，不是穷尽清单。它只能用来证明"官方承认的缺陷我们找得到"（recall 的**分子来源**），**不能当分母**。

### A4 VAmPI — **免费的官方安全孪生，本次第二个关键收获**

- 实测可达。官方机制（README / Dockerfile）：
  - 环境变量 `vulnerable=1`（默认，启用全部缺陷）/ `vulnerable=0`（**安全模式**）
  - 官方 `docker-compose.yaml` **同时起两个实例**：**:5001 secure（vulnerable=0）**、**:5002 vulnerable（vulnerable=1）**
  - 初始化：`GET /createdb`；API 规格：`/ui`（OpenAPI 3）
  - 官方缺陷清单共 **9 项**，含 BOLA、Mass Assignment、Excessive Data Exposure、Unauthorized Password Change、JWT weak-key bypass…
- **为什么这几乎是为我们设计的**：
  同一份代码、同一份 OpenAPI 3 规格、同一套端点、同一套数据库结构，**只切换授权检查**。
  → 这是**应用级配对的阴性对照**，比 v2 里"请求级幽灵对象对照"高一个证据层级。
  → 而且它是**官方特性**，不是我们注入的缺陷 → 直接削弱 v2 风险表里最凶的那条审稿攻击「自建 benchmark 是人为注入，不代表真实」。
  → 度量形式很干净：**合格 oracle 必须在 :5002 命中、在 :5001 静默。**
- **必须预注册的排除清单**：官方文档自承安全模式**并非完全干净**——
  > "Note that **even in secure mode (`vulnerable=0`), some endpoints may still have vulnerabilities** due to inherent bad practices in their implementation, such as the debug endpoint."
  → 起点：`/users/v1/_debug`（及其它经人工核对确认仍存在缺陷的端点）必须先冻结为排除清单，否则会被计入 FP。
  ```bash
  docker run -d -e vulnerable=0 -e tokentimetolive=3600 -p 5001:5000 erev0s/vampi:latest
  docker run -d -e vulnerable=1 -e tokentimetolive=3600 -p 5002:5000 erev0s/vampi:latest
  ```

### A5 BolaRay — 可得，但先做成本探测再承诺

- 实测 `github.com/BolaRay-d/BolaRay` 可达。
- 但运行链路重：`php2ast` → `TChecker` → `batch-import` → **Neo4j 2.1.8** → `python2 ./python-joern/bolaray --dal-specifications=...`
- 两个关键约束（对我们有利，应写进论文）：
  1. **需人工 DAL 规格**（`--dal-specifications`）→ 与 v2 的判断一致；
  2. **不支持 SELECT 路径**（仅覆盖缺失检查，且刻意忽略 SELECT 以压 FPR）→ 竞品差异的硬证据。
- **处置**：**不承诺数值比较**。先做一个**可行性探测**（能否在容器里跑通 1 个 PHP 应用）——
  跑不通就只作 related work；跑通了再在其原始 25 应用的重叠子集上报"共同对象集"上的结果。

### A6 BOLA-annotated OpenAPI 数据集 — 有用但必须降权

- `github.com/ejohansens/Vulnerable-APIs`：收录 11 个 API 的 OpenAPI 3.0 规格 + **逐端点 BOLA 标注**（VAmPI、crAPI、dvAPI、dvws、vulnerable-rest-api、RESTaurant、Juice Shop、Memos、Capital、vuln-bank、vapi）。
- **但**：1 star、无同行评审、无版本 pin。
- **处置**：仅用作**候选端点清单**，每一条**必须回到官方源（官方 challenges / README / CVE）核对后才能进真值**。

## 2. 拿不到的：原文证据

### N1 BACFuzz — 确认不可得

论文原文（arXiv:2507.15984）：
> "All identified issues have been responsibly disclosed, and **artifacts will be publicly released**."

→ 是**将来时**。当前无公开 artifact → v2 把它列为「强烈建议 baseline」**不成立**，必须移出。

### N2 BolaZ — 确认不可得

仅提供 `https://anonymous.4open.science/r/bolaz-96AC`（匿名仓，用于双盲评审，评审期结束后不保证存续）。

### N3 MOCGuard — **新识别的强竞品，须补进相关工作**

- Fengyu Liu, Youkun Shi, Yuan Zhang, et al. *MOCGuard: Automatically Detecting Missing-Owner-Check Vulnerabilities in Java Web Applications.* **IEEE S&P 2025**, pp. 903–919. （复旦大学）
- 做了什么：**数据中心**分析。先从数据库结构推断「用户表」与「用户拥有数据」，再在 **SQL 与 Java 两层**统一建模 owner-check（SQL 层：WHERE 子句含可信来源的用户列约束；Java 层：条件分支 / 等值比较 / post-dominator）。
- 数字：37 个应用（30 开源 + 7 工业），**161 个已确认 0-day，73 个 CVE**；相对复现的 **MACE-Java**：**Precision ↑31.31%、Recall ↑242.55%**（多检出 114 个）；效率约 76.22 s/应用（基于 CodeQL）。
- **为什么必须处理它**：它是 BolaRay 的 **Java 姊妹工作**，把「从数据库结构推断归属」这条线推到了 S&P 级别。
  → 结论强化：**静态归属推断这条线已被 CCS'24 + S&P'25 双点占住**，
  我们的差异**只能**落在「运行时 + 状态校准 + 可机检裁决」上，**不能再声称"推断归属"是贡献**。
- 可得性：未检索到公开代码仓 → 标 `未公开/待核实`，**不作 baseline**。

## 4. 关键推论：这对方案意味着什么

1. **BACFuzz 不可得，不构成致命伤。** 它本来是"最接近的工程竞品"，但**同语料的、可运行的、公开的**对照是 EvoMaster——而它恰好是**更该被比较的对象**（REST/API 安全测试的公开主线，且 Sah26 已把这条线做到 JSS）。
2. **EvoMaster 自己的文档替我们把立论写好了**（见下节原文）。这是本次核查最有价值的一条：
   我们不再需要"跑赢某个竞品"来立论——**SOTA 开源 fuzzer 的官方文档承认自己缺规格输入**。
3. **WFD 同源 → 可比性问题消失**；**VAmPI 孪生 → FPR 仪器免费到手**。
4. **论文定位必须再收紧一格**：从"比 SOTA 更好的检测器"改为
   **「给 BOLA 判定补上缺失的规格输入 + 状态校准裁决 + 可复现基准」**。
   理由：静态归属推断（BolaRay CCS'24 / MOCGuard S&P'25）与动态 fuzz（BACFuzz / ACBreaker）两条线都已占位，
   唯一还没被占的、且可实证的是 **oracle 校准与真值构造**。

## 5. 立论基石：EvoMaster 官方文档原文（`docs/faults.md`, fault code 306）

> **306 | Allowed To Modify Resource That Likely Should Had Been Protected**
> "BOLA and BFLA are major security vulnerabilities. To avoid users accessing protected resources, authorization mechanisms are usually put in place. However, it can happen that, on some endpoints, these authorization mechanisms are missing or misconfigured by mistake…
> However, **access policies could be arbitrarily complex**, where some users might validly interact with some resources of other users. A common example is 'administrator' users.
> **Without a formal specification describing in details the access policies in place, it is hard to say automatically if we are in the case of a BOLA/BFLA vulnerability. Still, some heuristics could be used to flag highly suspicious cases.**
> For example, if a user is blocked with a 403 to do a PUT and a PATCH on a resource, it would be quite suspicious if a DELETE would work just fine on that resource."

**三条可直接引用的要点**：

1. **它叫 "Likely Should Had Been Protected"**——命名本身就承认这是**猜测不是判定**；
2. **"Without a formal specification… it is hard to say automatically"**——SOTA 公开工具**自陈缺少访问策略规格输入**；
3. 它退守的启发式是「PUT/PATCH 被 403 但 DELETE 却成功就"很可疑"」——**没有对象归属证据，没有多账户差分，只有方法间不一致**。

同族的相邻 oracle（同为本文要超越的对照，一并纳入分析）：
- **304** Leakage Information Existence of Protected Resource（403/404 必须一致）
- **307** A Protected Resource Is Accessible Without Providing Any Authentication
- **308** Anonymous Modifications
- **310** Hidden Accessible Endpoint（影子端点）

> `待核实`：EvoMaster 是否支持外部传入访问策略规格（若支持，则"缺少规格输入"这条差异须改写成"规格须人工撰写 vs 自动带证据生成"）。
> 核验方式：读源码/文档中 `--expectations` 类参数，或跑 `evomaster --help`。**在核实前，论文里只引用上述原文，不做超出原文的断言。**
